# 가림(Garim)

> **외부 LLM API로 프롬프트가 나가기 전에, 로컬 컴퓨터에서 검사하는 프로그램.**
> 나가면 안 되는 정보(한국 개인정보·자격증명·기밀 표식)와 공격(프롬프트 인젝션·탈옥)을 찾는다.
>
> **상태: 설계 단계 (구현 전)** · Python · 솔로

**설계 문서: [docs/DESIGN.md](docs/DESIGN.md)** — 단일 자족 문서다.

---

## 무엇을 하는가

```
[내 앱·챗봇]  시스템 프롬프트 + 사용자 입력 + RAG 문서
      │
      ▼
┌──────────────────────────────┐
│  가림 검사기 (로컬, 오프라인)      │
│   L0  정규화 · 정규식 · 체크섬     │
│   L1  소형 모델 (PII NER · 공격)  │
│   판정: allow / mask / block    │
└──────────────────────────────┘
      │  통과분만, 필요시 마스킹된 상태로
      ▼
  Gemini API · OpenAI API
      │
      ▼  응답 받은 뒤 마스킹 토큰 복원
[내 앱]
```

**검사기 자체는 어떤 데이터도 외부로 보내지 않는다.** 개인정보를 탐지하려고 개인정보를 클라우드로 보내는 구성은 자기모순이기 때문이다. 이것이 로컬 실행의 유일한 이유이자 가장 중요한 성질이다.

세 가지로 쓸 수 있다 — **라이브러리**(`Inspector().check(text)`, 본체), **CLI**(`garim check`, CI·일괄 점검), **로컬 프록시**(`base_url`만 바꿔 코드 수정 없이).

## 무엇을 찾는가

**유출 위험** — 주민등록번호·외국인등록번호·여권·운전면허·사업자등록번호·법인등록번호·건강보험·계좌 8종을 **체크섬 검증**과 함께, 그리고 카드(Luhn)·전화·이메일·API 키·개인키·기밀 표식. 문맥에 의존하는 성명·주소는 학습한 NER이 맡는다.

**공격** — 직접·간접 프롬프트 인젝션, 탈옥, 시스템 프롬프트 탈취, 그리고 **한국어 고유 우회 벡터**(자모분해·초성체·로마자·한자혼용·조사파괴·존댓말 사회공학).

공격은 **두 축으로 분해한다**. *의도*(없음·인젝션·탈옥·시스템탈취)는 학습한 분류기가 4-way로 판정하고, *은닉*(base64·유니코드·homoglyph·자모분해·한자·공백파괴·전각 7종)은 **L0 정규화가 결정적으로** 판정한다. 은닉 축은 학습이 필요 없다 — 어느 정규화 규칙이 발동했는지가 곧 답이다. 이 분해가 "우회 벡터별 탐지율"을 측정 가능하게 만든다.

**섞인 입력을 세그먼트로 나눠 본다.** 실제 프롬프트는 산문 + 코드 블록 + JSON이 뒤섞여 있고, **코드에서는 변수명이 PII처럼 보인다**(`user_name`, `ssn_field`). 그래서 세그먼트마다 타입을 결정적 규칙으로 판별해 정책을 전환한다 — 코드에서는 PII 임계를 완화하되 **시크릿은 강화**하고, JSON에서는 키 이름을 빼고 값만 검사한다. 축마다 방향이 다르다. 조사 범위에서 이걸 제품 기능으로 문서화한 사례를 찾지 못했다.

## 설계의 중심 — 가역 정규화 후 재검사

우회 방어를 분류기가 아니라 **결정적 정규화**에 둔다.

```
원문 ─────────────────────────► [검사 1] 원문
  │
  ▼ NFKC → 제로위드 제거 → homoglyph 정규화
    → 자모 조합 복원 → 한자→한글 → 공백 정규화 → base64 디코드
  │
  ├─────────────────────────► [검사 2] 정규화본
  │
  ▼
  [검사 3] ★ 고정밀 규칙의 발동 자체가 은닉 시도 신호 ★
```

실측으로 한 번 교정했다. 처음엔 "델타 총량"을 신호로 쓰려 했는데 **틀렸다** — 들여쓰기 있는 정상 문서가 델타 0.346으로 어떤 우회 시도보다 높았다. 규칙별로 나눠 보니 **제로위드·태그문자·homoglyph·자모조합은 정상 발동 0/10**(고정밀), 전각·한자·공백은 정상도 발동(저정밀)이었다.

그래서 **고정밀 규칙의 발동만 신호로 쓰고, 나머지의 가치는 재검사에 둔다** — `無視`를 `무시`로 바꾼 뒤 다시 검사해 공격이 잡히는 것이 목적이지 "한자가 있었다"는 사실 자체는 신호가 아니다. 설명 가능하고, 우회가 어렵고, 학습이 필요 없다. 재현: [normalize_probe.py](docs/normalize_probe.py)

## 왜 의미가 있는가

국내에 같은 범주 상용 제품이 최소 8종 있지만 **오탐률(FPR)을 수치로 공개한 곳이 하나도 없다.** 한국어 프롬프트 DLP의 공개 비교 벤치마크도 없다.

탐지기가 아예 없는 건 아니다 — Google Cloud SDP에 한국 infoType 6종이 있고 Model Armor는 한국어를 공식 지원한다. **다만 둘 다 프롬프트를 클라우드로 보낸다.** 그래서 갭은 "탐지기가 없다"가 아니라 **"데이터를 내보내지 않고 쓸 수 있는 탐지기가 없다"** 이다. 개인정보보호법이 법적 근거 없는 주민등록번호 처리를 금지(유출 시 최대 5억원)한다는 점을 고려하면 더욱 그렇다.

체크섬 효과는 **측정 전에 예측값이 있다.** 현실적 오탐원(주문번호·입사일 기반 사번·송장번호) 각 2만 건으로 쟀더니, **주민등록번호는 3중 검증(체크섬 + 생년월일 유효성 + 성별코드 정합)으로 약 250배**, 사업자·법인·카드는 체크섬만 있어 **약 10배** 오탐이 줄었다. 실측이 이 범위를 벗어나면 코퍼스나 구현을 의심할 근거가 된다. 재현: [fpr_probe.py](docs/fpr_probe.py)

## 기술 스택 (계획)

브리프가 *"프로그램은 온디바이스 모델, Google 모델(gemma4) 선호, 사용 목적에 따라 BERT도 가능, 라이선스 확인"* 을 요구한다.

조사 결과 **Gemma 4로는 분류를 할 수 없다** — transformers의 `gemma4` 모듈에 토큰 분류·시퀀스 분류 헤드가 하나도 없고 추가 PR은 보류 상태다. 분류가 되는 Gemma 파생(EmbeddingGemma·T5Gemma 2)으로 내려가면 Apache 2.0을 잃고 Gemma Terms of Use가 된다.

**그래서 계열을 선호도가 아니라 태스크 성격으로 나눈다.**

| 태스크 | 계열 | 이유 |
|---|---|---|
| **판별** (토큰 분류·시퀀스 분류) | **BERT 계열 인코더** | 양방향 어텐션이 필수다. NER은 뒤 문맥을 봐야 경계를 정한다. 디코더의 인과 마스크는 구조적으로 불리하고, 소형이라 CPU에서 예측 가능하다 |
| **생성·판정** (자유 서술) | **Gemma 4** | Apache 2.0이고 Google 모델. 정책을 프롬프트로 주고 판정시키는 자리 |

**Gemma 4에 분류 헤드가 없는 건 결함이 아니라 설계 의도다** — 생성 모델이니까. 판별에는 판별용 아키텍처를 쓴다.

| 역할 | 채택 | 라이선스 |
|---|---|---|
| L1 백본 (PII NER 29라벨 + 공격 4-way + 보조 헤드 2) | **`skt/A.X-Encoder-base`** (한국어 ModernBERT, 0.1B, 16k) | **Apache 2.0** |
| ↳ W1 실측 대안 | EmbeddingGemma 300m / T5Gemma 2 270m-270m (실측 ~0.79B) | Gemma ToU · gated |
| L2-fast (선택, 상시 상주) | **`kanana-safeguard-prompt-2.1b`** — 공격 의도 전담 | Apache 2.0 |
| L2-judge (선택, 온디맨드) | **`Qwen3Guard-Gen-4B`** (대안 `guardrail-korean-gemma-4-E2B`) | Apache 2.0 / Gemma ToU |
| R2 교사 | `kanana-safeguard-prompt-2.1b` + **Gemma 4 E2B 병행** (합의를 라벨로) | Apache 2.0 · Gemma ToU |
| 추론 | ONNX Runtime INT8 | MIT |
| 검사 대상 업스트림 | Gemini API · OpenAI API | — |

**L2를 두 모델로 나눈 이유**는 라우팅이 좋아서가 아니다. 조사해 보니 축이 넷(PII 문맥·공격 의도·기밀 판단·시크릿 플레이스홀더)인데 **특화 모델이 존재하는 축은 하나뿐**이고, 라우팅 연구(RouteGuard)의 in-domain 이득은 0.2~0.4포인트에 그친다. 그래서 **공격 의도만 저렴한 2.1B에 상주시키고(단일 토큰 디코드라 밀리초급), 나머지 셋은 온디맨드 judge 하나가 정책 프롬프트를 갈아 끼워 처리**한다. 상용 제품들이 실제로 쓰는 구조이기도 하다 — 작은 전용 검출기 다수 + 큰 judge 하나.

기본값은 Apache 2.0인 A.X-Encoder다. 다만 Gemma 계열 인코더 파생이 더 나은지는 **W1에 CPU 지연·한국어 F1·메모리·라이선스 네 기준으로 실측 비교**하고, 어느 쪽을 택하든 근거를 수치로 공개한다.

`openai/privacy-filter`는 **실측으로 기각했다** — M2 MacBook MPS 중앙값 958ms(CPU는 2~3배 느림). "활성 50M"이 CPU 지연으로 번역되지 않는다.

## 학습

로컬 실행 제약에서 따라오는 두 개만 한다. 합쳐 **약 35 GPU-h**다.

- **R1 — 한국 PII NER**(29 라벨): 어떤 공개 모델도 한국 고유 식별자 태그를 갖고 있지 않다
- **R2 — 공격 분류기 distillation**: 교사 2.1B를 노트북에 상주시킬 수 없다. 0.1B로 줄이지 않으면 로컬 실행이 성립하지 않는다

R2는 **교사를 둘 쓴다.** `kanana-safeguard-prompt-2.1b`의 출력이 SAFE/인젝션/리킹 셋뿐이라 **탈옥에 해당하는 클래스가 없기** 때문이다. Gemma 4 E2B를 정책 프롬프트로 병행시키고 **두 교사가 합의한 것만 라벨로 채택**하며, 불일치는 학습에서 빼고 검토 큐에 쌓는다.

학습 데이터는 라이선스가 선택을 결정했다. **KDPII**(CC-BY-4.0), **PolyGuardPrompts**(CC-BY-4.0, 한국어 포함), **자체 합성 코퍼스**(주력)를 쓰고, `korean_unsmile`(CC-BY-NC-ND)과 **AI-Hub 전체**는 제외한다.

## 이전 방향

`docs/plan/`은 더 넓은 범위(에이전트 게이트웨이·MCP)를 다뤘던 이전 설계다. 범위 4.3배 초과와 설계 결함으로 대체됐고, 사유는 [docs/plan/README.md](docs/plan/README.md)에 있다. 시장 조사와 라이선스 심사는 여전히 유효해서 남겨뒀다.

`src/`·`eval/`·`data/`의 코드는 그 이전 프로젝트(SafeAgent-KR)의 산출물이다. 마지막 완전 상태는 커밋 `74e1ae7`에 봉인돼 있다.

## 라이선스

**Apache-2.0**. CredSweeper(MIT)·ONNX Runtime(MIT)·A.X-Encoder(Apache-2.0) 임포트 결합이 전부 문제없고, 특허 조항이 있어 상용 채택에 유리하다. GPL 계열은 택하지 않는다 — trufflehog(AGPL-3.0)를 기각한 것과 같은 이유다.

학습 데이터도 같은 기준으로 걸렀다. 허용은 **Apache-2.0 / MIT / CC-BY-4.0 / CC0**뿐이고, 검증 스크립트가 **HuggingFace API를 런타임에 조회**해 강제한다 — 문서에 적힌 라이선스 문자열을 읽지 않는다. 실제로 PolyGuardPrompts를 ODC-BY로 잘못 적어 뒀다가 CC-BY-4.0으로 정정한 적이 있어서, 문서를 진실의 원천으로 삼으면 그 오류가 그대로 통과한다.
