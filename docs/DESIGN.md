## 0. 요약

**외부 LLM API로 프롬프트가 나가기 전에, 로컬 컴퓨터에서 검사하는 프로그램.** 나가면 안 되는 정보(한국 개인정보·자격증명·기밀 표식)와 공격(프롬프트 인젝션·탈옥)을 찾는다. **검사기 자체는 어떤 데이터도 외부로 보내지 않는다.**

| | |
|---|---|
| **형태** | Python 라이브러리(본체) + CLI + 로컬 프록시(선택) |
| **탐지** | 유출 21종 · 공격 15종 — 공격은 **의도 4 × 은닉 7**로 분해한다 (§2) |
| **계층** | L0 규칙·정규화 → L1 소형 모델(백본 1 + 헤드 3) → L2 로컬 LLM 2종(선택) |
| **핵심 설계** | **가역 정규화 후 재검사** — 우회 방어를 분류기가 아니라 결정적 규칙에 둔다 (§2.3) |
| **모델** | 판별은 BERT 계열 인코더, 생성·판정은 Gemma 4 (§4) |
| **학습** | R1 한국 PII NER(29 라벨) · R2 공격 분류기 distillation(교사 2종) — **~35 GPU-h** (§6) |
| **헤드라인 지표** | 유형별 탐지 F1 **+ 같은 표의 FPR** / 우회 벡터별 탐지율 **+ 정상 오탐률**. 목표 수치는 §7.1.1 |
| **일정** | 필수 **51.5일** (+선택 4.5) — 5주 초과를 시작 전에 명시 (§8) |

**차별화 여덟** (상세 §9)

1. 한국 고유 식별자 8종 + **체크섬 검증** — 클라우드(Google SDP)에는 있지만 **데이터를 내보내지 않고 쓸 수 있는 것**이 없다
2. **가역 정규화 후 재검사** — 설명 가능하고 우회가 어렵고 학습이 필요 없다
3. **고정밀 정규화 규칙의 발동을 회피 신호로** — 델타 총량은 신호가 아니라는 것도 실측으로 확인했다 (부록 A.2)
4. **token efficiency의 한국어 역전 발견** — 최신 시크릿 탐지 기법이 한국어에서 신호가 뒤집힌다는 것을 실측했다 (부록 A.3)
5. **한국어 우회 벡터 벤치마크 + 한국어 시크릿 평가셋** — 둘 다 공개 자산이 없다
6. **FPR 공개** — 국내 8개 제품 중 오탐률을 수치로 공개한 곳이 하나도 없다
7. **온디바이스가 치르는 정확도 대가의 정량화** — Gemini 기준선과의 격차를 공개한다 (§7.4)
8. **입력 타입 조건화 PII 판정** — 코드·JSON·로그가 섞인 프롬프트에서 정책을 세그먼트 단위로 자동 전환한다 (§2.6). **ON/OFF 대조로 기여를 정량화하고, 기여가 없으면 잘라낸다**

## 1. 무엇을 만드는가

**외부 LLM API로 프롬프트가 나가기 전에, 로컬 컴퓨터에서 검사하는 프로그램.**

두 가지를 본다.

- **유출 위험** — 나가면 안 되는 정보가 프롬프트에 있는가 (한국 개인정보, 자격증명, 기밀 표식)
- **공격** — 프롬프트에 인젝션·탈옥 시도가 섞여 있는가 (내 사용자 입력이나 RAG 문서를 통해 들어온 것)

```
[내 앱·챗봇]
  시스템 프롬프트 + 사용자 입력 + RAG 문서
        │
        ▼
  ┌──────────────────────────────┐
  │  가림 검사기 (로컬, 오프라인)      │
  │   L0 규칙 · 정규화 · 체크섬       │
  │   L1 소형 모델 (PII NER · 공격)  │
  │   판정: allow / mask / block    │
  └──────────────────────────────┘
        │  통과분만 (필요시 마스킹된 상태로)
        ▼
  Gemini API · OpenAI API · …
        │
        ▼  응답 수신 후 마스킹 토큰 복원
  [내 앱]
```

**검사기 자체는 어떤 데이터도 외부로 보내지 않는다.** 개인정보를 탐지하려고 개인정보를 클라우드로 보내는 구성은 자기모순이기 때문이다. 이것이 로컬 실행의 유일한 이유이자 가장 중요한 성질이다.

### 1.1 세 가지 사용 방식

| 방식 | 형태 | 대상 |
|---|---|---|
| **라이브러리** (핵심) | `Inspector().check(text)` | 앱에 직접 임베드 |
| **CLI** | `garim check "..."` / stdin 파이프 / `garim scan dir/` | 스크립트·CI·일괄 점검 |
| **로컬 프록시** (선택) | OpenAI 호환 `localhost:8080` | 앱 코드 수정 없이 `base_url`만 교체 |

라이브러리가 본체이고 나머지 둘은 얇은 껍데기다. 프록시는 편의 기능이지 아키텍처가 아니다.

### 1.2 두 가지 동작 모드

지연 허용치가 다르다.

| 모드 | 계층 | 지연 | 용도 |
|---|---|---|---|
| **`interactive`** (기본) | L0 + L1 | 목표 **p50 300ms** / **p95 900ms**(다중 세그먼트, §7.1.3) | 대화형 앱의 매 요청 |
| **`thorough`** | L0 + L1 + L2(2종) | 수 초 허용 | CI·일괄 점검·의심 케이스 재검사 |

> **사전 검사는 인라인 프록시가 아니므로 지연 압박이 작다.** 뒤따르는 LLM API 호출 자체가 수 초 걸리므로, 검사 300ms는 체감 비용이 아니다. 이 여유가 설계를 훨씬 단순하게 만든다.

### 1.3 범위 밖 — 명시적으로

| 안 하는 것 | 이유 |
|---|---|
| 에이전트·도구 호출·MCP | 별개 문제. 검사기는 텍스트만 본다 |
| 조직 차원 강제 | 사용자가 끌 수 있다. IT 통제가 아니라 개발자·분석가가 켜는 안전장치 |
| 응답(출력) 모더레이션 | 유해성 판정은 별개 축. 마스킹 복원만 한다 |
| 이미지·파일 파싱 (OCR·HWP) | 텍스트 입력만 |
| 다국어 | 한국어 + 영어 |
| 실시간 스트리밍 검사 | 사전 검사이므로 불필요 |

**체크섬이 L0의 핵심이다.** 정규식만 쓰면 주문번호·사번·제품 시리얼처럼 형식이 유사한 문자열을 전부 오탐한다. **엔티티별로 예측값을 계산해 뒀다** — 측정 전에 기대치를 갖는 드문 지표다.

**1차: 무작위 숫자열 기준** ([checksum_probe.py](checksum_probe.py), 각 10만 건)

주민번호 9.89% · 사업자 9.97% · 법인 10.03% · Luhn 9.99% 통과 → **체크섬 하나로 약 10배 감소.**

**2차: 현실적 오탐원 기준** ([fpr_probe.py](fpr_probe.py), 각 2만 건). 실제 업무 문자열(주문번호 `YYMMDD-일련번호`, 입사일 기반 사번, 송장번호)로 다시 쟀더니 **주민번호는 훨씬 크게 줄었다.**

| 오탐원 | 정규식 단독 | +체크섬 | **+생년월일·성별코드 정합** | 감소 배수 |
|---|---|---|---|---|
| 주문번호 | 88.9% | 8.8% | **0.34%** | **265배** |
| 사번(입사일 기반) | 100% | 10.2% | **0.43%** | **235배** |
| 송장번호 | 100% | 9.7% | **0.36%** | **282배** |
| 제품 시리얼 (사업자 형식) | 100% | 10.1% | — | 10배 |

→ **주민등록번호·외국인등록번호는 3중 검증(체크섬 + 생년월일 유효성 + 성별코드 정합)으로 약 250배**, **사업자·법인·카드는 체크섬만 있어 약 10배**가 예측값이다. 실측이 이 범위에서 크게 벗어나면 코퍼스나 구현을 의심한다.

⚠️ 여권·운전면허·계좌·건강보험은 체크섬이 없어 이 예측이 적용되지 않는다. 사전 크기에 의존하며 별도로 측정한다.

### 2.2 공격 (Attack) — 두 축으로 분해한다

15개 공격 코드는 **직교하는 두 축**이다. 이 분해가 설계 전체를 규정한다.

| 축 | 무엇을 묻는가 | 판정 주체 |
|---|---|---|
| **의도** | 무엇을 하려는가 | **L1-ATK 분류기** (학습 R2) |
| **은닉** | 어떻게 숨겼는가 | **L0 정규화** (결정적, 학습 없음) |

**은닉 축은 학습이 필요 없다.** 정규화 체인이 어느 규칙을 발동시켰는지가 곧 답이고, 고정밀 규칙 4종은 정상 한국어에서 발동률 0%임을 실측했다(부록 A.2).

#### 2.2.1 의도 축 — L1-ATK가 판정 (4-way)

| 의도 클래스 | 대응 코드 | 설명 |
|---|---|---|
| `NONE` | — | 공격 아님 |
| `INJECTION` | **A-INJ-01** 직접 인젝션 (이전 지시 무시·덮어쓰기)<br>**A-INJ-02** 간접 인젝션 (RAG·웹 콘텐츠에 심긴 지시) | 01/02 구분은 `Segment.origin`으로 (§3.2) |
| `JAILBREAK` | **A-JB-01** 역할극 탈옥 (DAN류)<br>**A-JB-02** 가상 시나리오·조건부 우회 | 세부 구분은 보조 신호와 규칙으로 |
| `SYSTEM_LEAK` | **A-LEAK-01** 시스템 프롬프트 탈취 시도 | 규칙(고정 문구)과 병용 |

#### 2.2.2 은닉 축 — L0가 결정적으로 판정 (7종)

| 코드 | 유형 | 정규화 단계 | 정상 발동률 |
|---|---|---|---|
| **A-ENC-01** | base64 / hex 인코딩 은닉 | ⑦ 디코드 | 저정밀 |
| **A-ENC-02** | 유니코드 은닉 (zero-width, 태그 문자 U+E0000) | ② 제거 | **0/10 고정밀** |
| **A-ENC-03** | homoglyph (시각적 동형 문자) | ③ confusable 정규화 | **0/10 고정밀** |
| **A-KO-01** | **자모 분해** (`무시해` → `ㅁㅜㅅㅣㅎㅐ`) | ④ 자모 조합 복원 | **0/10 고정밀** |
| **A-KO-04** | **한자 혼용** (`無視`) | ⑤ 한자→한글 | 저정밀 (한자 병기는 정상) |
| **A-KO-05** | **조사·띄어쓰기 파괴** (`이 전 지 시 무 시`) | ⑥ 공백 정규화 | 저정밀 |
| **A-MISC-01** | 전각 문자 혼입 | ① NFKC | 저정밀 |

#### 2.2.3 축에 안 들어가는 둘 — L1 보조 헤드

| 코드 | 유형 | 왜 별도인가 | 판정 |
|---|---|---|---|
| **A-KO-02** | **초성체** (`ㅁㅅㅎ`) | 정규화로 복원하려면 사전이 필요하고 1:N 모호 | L0 사전 + **L1 보조** |
| **A-KO-03** | **로마자 표기 우회** (`musihae`) | 로마자→한글 역변환이 1:N이라 결정적 정규화 불가 | **L1 보조 헤드 A** (sigmoid) |
| **A-KO-06** | **존댓말 사회공학** ("상무님 지시로…") | 은닉이 아니라 **표현 방식**. 정상 문장일 수도 있다 | **L1 보조 헤드 B** (sigmoid) |

#### 2.2.4 코드 조합 — `Finding`을 어떻게 채우는가

```
L1 의도 판정: INJECTION          →  code = "A-INJ-01"
L0 은닉 판정: 자모 조합 복원 발동   →  evasion = ["A-KO-01"]
L1 보조 헤드 A: 로마자 = true      →  evasion += ["A-KO-03"]

최종: Finding(code="A-INJ-01", evasion=["A-KO-01","A-KO-03"], layer="L1")
```

**이 분해가 H2("우회 벡터별 탐지율")를 측정 가능하게 만든다** — 은닉 벡터별로 의도 탐지가 유지되는지 보면 된다.

⚠️ **A-KO-01~06이 차별화 지점이다.** 한국어 고유 우회 벡터를 체계적으로 다룬 공개 자산을 확인하지 못했다. CAGE/KoRSET(ICLR 2026)이 *"직역한 영어 인젝션으로 학습하면 한국 특유의 공격을 놓친다"*를 실증했으므로, 번역 데이터에만 의존하지 않는 것이 근거 있는 선택이다.

### 2.3 핵심 설계 — 가역 정규화 후 재검사

우회 방어를 **분류기가 아니라 결정적 정규화**에 둔다. 이게 이 설계의 중심 아이디어다.

```
원문
 │
 ├─────────────────────────────► [검사 1] 원문 그대로
 │
 ▼ 정규화 체인
   ① NFKC (전각·호환문자)
   ② zero-width / 태그 문자 제거
   ③ homoglyph → 표준 문자 (Unicode confusables)
   ④ 자모 조합 복원 (ㅁㅜㅅㅣ → 무시)
   ⑤ 한자 → 한글 (선택, 사전)
   ⑥ 공백·구두점 정규화
   ⑦ base64/hex 디코드 (형태가 맞을 때만)
 │
 ├─────────────────────────────► [검사 2] 정규화본
 │
 ▼
 [검사 3] ★ 고정밀 규칙(②③④)의 발동 자체를 신호로 ★
         (①⑤⑥⑦은 정상 한국어도 발동 — 재검사 수단일 뿐)
```

**주의: 델타 총량은 신호가 아니다.** 프로토타입 실측에서 들여쓰기 있는 정상 문서가 델타 0.346으로 어떤 우회 시도보다 높았다. 규칙별로 갈린다 — 제로위드·태그문자·homoglyph·자모조합은 정상 발동 **0/10**(고정밀), 전각·한자·공백은 정상도 발동(저정밀). **고정밀 규칙의 발동만 신호로 쓰고, 저정밀 규칙의 가치는 재검사에 둔다.** 상세는 [부록 A.2](#a2-정규화-체인--델타-총량은-신호가-아니다).

### 2.4 시크릿 탐지 — 코드 스캐너를 그대로 쓰면 안 된다

**기성 시크릿 스캐너는 코드 저장소용이고 산문에 잘 전이되지 않는다.** CredData 벤치마크(코드 기준인데도) precision을 보면 명확하다.

| 도구 | Precision | Recall | F1 |
|---|---|---|---|
| **CredSweeper** (Samsung, **MIT**, Python 네이티브 + ML) | **0.9165** | 0.8075 | **0.8586** |
| gitleaks | 0.5256 | 0.2444 | 0.3336 |
| **detect-secrets** (LLM Guard가 쓰는 것) | **0.1416** | 0.3814 | 0.2065 |

산문에 가장 가까운 실증은 MSR 2026의 GitHub 이슈 연구(자유 산문 54,148건)인데, 결론이 *"regex·엔트로피 기반은 recall은 높지만 precision이 형편없다"* 였다. GitGuardian이 **마크다운 확장자를 스캔 대상에서 제외**하는 것도 같은 이유다 — 문서가 이미 그 정도면 자유 프롬프트는 더 심하다.

**그래서 3단 구조로 간다.**

```
(A) 고정밀 prefix 규칙  → 항상 실행. 오탐 거의 0
     PEM 헤더, sk-ant-, sk-proj-, AKIA/ASIA, ghp_/github_pat_,
     xoxb-/xapp-, AIza, glpat-, hf_, test_sk_/live_sk_, KakaoAK …
(B) 저정밀 휴리스틱     → 컨텍스트 게이트 통과 시에만
     일반 고엔트로피·generic keyword
(C) 애매한 것          → 차단이 아니라 사용자 확인
```

**채택**: CredSweeper(MIT, Python 임포트 가능, F1 0.8586)를 (A)(B)의 기반으로 쓰고 국내 패턴을 추가한다.
**기각**: `trufflehog`는 **AGPL-3.0**이라 임포트 결합 시 전염 위험이 있고, 무엇보다 **live verification이 후보 시크릿을 외부 API로 전송**한다 — "외부로 나가기 전에 막는다"는 목적과 정면 충돌이다. `ggshield`도 원문을 클라우드로 보내므로 같은 이유로 배제.

**국내 서비스 키 앵커** (L-SEC-02)

| 대상 | 앵커 |
|---|---|
| 토스페이먼츠 | `test_sk_`, `live_sk_` (API 연동) / `test_gsk_`, `live_gsk_` (결제위젯) |
| 카카오 | **`KakaoAK ` 헤더 문자열** — 키 자체보다 이 앵커가 신뢰도 최상 |
| 네이버 클라우드 | 헤더명 `x-ncp-iam-access-key`, `x-ncp-apigw-api-key` |
| 공공데이터포털 | `serviceKey=` 파라미터 — shape보다 키워드가 정확 |
| 공동인증서(NPKI) | 파일명 `signCert.der`·`signPri.key`, 경로 `AppData\LocalLow\NPKI` |

⚠️ **OpenAI 키 형식이 바뀌었다.** 현행은 `sk-proj-`·`sk-svcacct-`·`sk-admin-`이고 **본문에 `-`/`_` 구분자가 포함**된다. 구식 `sk-[A-Za-z0-9]{48}`은 **탐지 실패(fail-open)** 하므로 `sk-(proj|svcacct|admin)-[A-Za-z0-9_\-]{20,}`로 잡아야 한다.

**주의: token efficiency는 한국어에서 신호가 역전된다.** 한국어 산문 평균 eff 1.08이 실제 시크릿 1.48보다 낮아, 임계 2.5를 그대로 적용하면 **한국어 문장 100%가 오탐**된다. ASCII 게이트로 100%→0%가 되는 것까지 확인했다. 상세는 [부록 A.3](#a3-token-efficiency의-한국어-역전).

### 2.5 기밀 표식 — 근거와 위치 가중치

**법적·표준 근거가 있다.**

| 근거 | 내용 |
|---|---|
| **보안업무규정** (대통령령) | I·II·III급비밀 3등급 + **대외비**를 정의한다. ⚠️ **표시 방법의 세부(붉은색·위치)는 대통령령이 아니라 「보안업무규정 시행규칙」 소관**이다 — 비밀문서는 앞뒤 표지와 각 면 상하단 중앙에 붉은색 표시, 대외비는 표면 중앙 상단에 붉은색 예고문 |
| **ISMS-P 2.1.3** | "정보자산별 **보안등급(기밀, 대외비, 일반 등)**을 식별할 수 있도록 표시" — 전자문서는 표지 또는 워터마킹 |
| **부정경쟁방지법** 제2조2호 | 영업비밀의 **비밀관리성** 요건 충족을 위해 실무상 "첫 페이지나 머리글에 '영업비밀', '대외비' 명확 표기" 권고 |
| ISO/IEC 27001:2022 A.5.13 | DLP가 읽고 동작할 수 있는 라벨 부여 요구 |

**사전** — 근거 있는 것(`대외비`, `기밀`, `비밀`, `영업비밀`, `I급비밀`~`III급비밀`, `보안등급`, `예고문`), 실무 관행(`극비`, `사내한`, `내부용`, `취급주의`, `관계자 외 열람 금지`, `무단 배포 금지`, `사외비`, `부외비`, `秘`/`極秘`), 영문(`CONFIDENTIAL`, `INTERNAL USE ONLY`, `RESTRICTED`, `PROPRIETARY`, `DO NOT DISTRIBUTE`, `TLP:RED`/`TLP:AMBER`).

**단순 substring 매칭은 오탐이 심하다** — "이거 대외비인데 물어볼게요" 같은 일상 표현이 흔하다. **위치 가중치**를 준다.

| 신뢰도 | 조건 |
|---|---|
| **높음** | 문서 첫 3줄 이내 · 단독 라인 · 「」·[]·【】로 감쌈 · 등급 표기 동반(`보안등급: 대외비`) · 전각/공백 강조형(`대 외 비`) |
| **낮음** | 문장 중간에 조사 결합 (`대외비인데`, `대외비라서`) |

**기밀 표식은 `block`이 아니라 `warn`이다.** 시크릿과 달리 오탐 비용이 사용자 경험을 크게 해친다. `보안` 같은 단독 단어는 오탐이 극심하므로 사전에서 제외한다.

**위치 가중치를 실측했다** ([marker_probe.py](marker_probe.py), 기밀문서 5건 · 일상 언급 5건).

| 방식 | 재현율 | 오탐율 |
|---|---|---|
| 단순 substring 매칭 | 100% | **80%** |
| **위치 가중치** (첫3줄 +2 / 단독·괄호 +3 / 등급표기 +3 / 조사결합 −3, 임계 3) | 100% | **0%** |

"이거 대외비인데 물어봐도 될까요?", "기밀 유지 서약서 양식을 찾고 있어요" 같은 일상 언급이 전부 걸러진다. ⚠️ 표본 10건이라 임계값은 실제 코퍼스로 재조정해야 한다.


### 2.6 입력 타입 조건화

**코드에서는 변수명이 PII처럼 보인다**(`user_name`, `phone_number`, `ssn_field`). LLM 프롬프트에는 코드가 흔히 섞이므로 예외가 아니라 상시 상황이다.

조사 범위에서 **"입력이 코드/JSON/로그인지 자동 판별해 PII 정책을 전환한다"를 제품 기능으로 문서화한 사례도, 정면으로 다룬 논문도 확인하지 못했다.** GitHub Secret Scanning의 "테스트 파일 제외 / 한 파일에 오탐 5건 누적 시 알림 중단"이 가장 가까운 실무 선례이나 이건 파일 종류 기반이지 내용 기반 자동 판별이 아니다. Presidio가 주는 것도 정적 allow list·임계값뿐이다.

⚠️ "없다"는 검색 실패일 수 있다. 단정하지 않는다.

#### 2.6.1 세그먼트 단위 — 문서 단위가 아니다

실제 프롬프트는 산문 + 코드 블록 + JSON이 섞여 있다. 문서 전체에 타입 하나를 붙이면 의미가 없다. `Segment`(§3.2)가 `content_type`을 갖는다.

호출자가 세그먼트를 안 나눠 주면 검사기가 **자동 분할**한다 — 코드 펜스(` ``` `), 연속 들여쓰기 블록, JSON 객체 경계 기준.

#### 2.6.2 타입 감지 — 결정적 규칙 (L0, 예산 < 5ms)

| 타입 | 판정 신호 | 임계 |
|---|---|---|
| `structured` | `json.loads` 또는 YAML 파싱 성공 | 성공 = 확정 |
| `code` | 코드 펜스 · 언어 키워드 밀도(`def`/`function`/`import`/`const`) · 중괄호·세미콜론 줄 비율 · 식별자 패턴(snake_case·camelCase) 밀도 | 가중합 ≥ 0.5 |
| `log` | 타임스탬프 패턴 줄 비율 · 로그 레벨 토큰(`INFO`/`ERROR`/`WARN`/`DEBUG`) · 줄 길이 분산 | 줄의 60% 이상 |
| `prose` | 기본값. **한글 조사 밀도**가 보조 신호 | — |
| `unknown` | 어느 것도 아님 | **prose 정책 적용 + 로그 기록** |

⚠️ **오분류가 오탐보다 위험하다** — 산문을 `code`로 잘못 보면 PII 임계값이 올라가 **미탐**이 된다. **불확실하면 `prose`(가장 엄격)로 폴백**한다. fail-closed 원칙(§3.6)의 연장이다.

#### 2.6.3 정책 전환 — 축마다 방향이 다르다

**단순히 "임계값을 올린다"가 아니다.** 코드에서는 PII 오탐이 늘지만 **시크릿 진탐도 늘어난다.**

| 타입 | PII | 시크릿 | 공격 |
|---|---|---|---|
| `prose` | 기본 | 기본 | 기본 |
| `code` | **완화** — PERSON/ADDRESS 임계 +0.15, 식별자 allow list | **강화** — 코드에 진짜 키가 많다 | **완화** — 주석 속 지시문은 인젝션이 아니다 |
| `structured` | **키 이름 제외, 값만 검사** | 강화 (`.env` 형식) | 기본 |
| `log` | IP·타임스탬프·UUID 오탐 억제 | 기본 | 완화 |

#### 2.6.4 키/값 분리 — §2.4와 대칭

```
user_name = "김철수"          →  좌변 user_name = 검사 제외 (식별자)
                                 우변 "김철수"  = PII 탐지 ✅
{"phone": "010-1234-5678"}   →  키 "phone" 제외, 값만 검사
```

**§2.4의 시크릿 `.env` 규칙과 정확히 대칭이다.** 시크릿에서는 키 이름이 **신호**(`API_KEY=`)인데 PII에서는 키 이름이 **노이즈**다. 같은 파서를 쓰고 판정만 반대로 한다.

**코드 식별자 allow list** — `user_name`, `phone_number`, `ssn`, `email`, `address`, `birth_date`, `card_no`, `account` 등. 이름 자체는 PII가 아니다.

#### 2.6.5 L1 모델과의 관계

타입을 L1 입력 feature로 넣을 수도 있으나(정규화 델타처럼 concat), **기본은 정책 전환만 한다.** 이득 대부분이 후처리 필터링(키 제외·allow list·임계값)에서 나오고, 모델에 넣으면 타입별 학습 데이터가 필요해져 합성 코퍼스가 4배가 된다.

→ **W5에 측정한다.** 정책 전환만으로 타입별 FPR이 목표(§7.1) 안에 들어오면 모델 feature는 넣지 않는다. §8.4의 절삭 가능 항목이다.

## 3. 시스템 구성

### 3.1 계층

| 계층 | 하는 일 | 학습 | 지연(목표) | 필수 |
|---|---|---|---|---|
| **L0** | 정규화 체인 + 정규식 + 체크섬 + 시크릿 패턴 + 엔트로피 + 기밀 표식 | ❌ 규칙 | < 20ms | ✅ |
| **L1-PII** | 문맥 의존 PII 토큰 분류 (29 라벨) | ✅ **R1** | < 150ms | ✅ |
| **L1-ATK** | 공격 의도 4-way + 보조 헤드 2 | ✅ **R2** | < 100ms | ✅ |
| **L2-fast** | 공격 의도 재판정 (kanana 2.1b, 상주) | ❌ | 수백 ms | 선택 |
| **L2-judge** | PII 문맥·기밀·플레이스홀더 (온디맨드) | ❌ | 수 초 | 선택 |

지연은 **세그먼트 1개 기준**이다. 다중 세그먼트 예산은 §7.1.3.

**★ L1은 정규화본에만 1회 돈다.** 원문은 L0만 본다 — L1을 원문과 정규화본에 각각 돌리면 지연이 2배가 되고, 정규화는 가역이므로 정규화본에서 찾은 스팬을 §3.2.4 역매핑으로 원문 위치로 되돌리면 된다. **L1-PII와 L1-ATK는 백본을 공유하므로 인코더 forward도 1회**이고 헤드만 갈라진다(§4.2).

**L0만으로도 제품이 성립한다.** L1은 L0가 원리적으로 못 잡는 것(문맥 의존)을 담당하고, L2는 `thorough` 모드 전용이다. 이 순서가 곧 절삭 순서이기도 하다(§8.4).

### 3.2 입력·출력 데이터 구조

#### 3.2.1 입력 — 세그먼트

```python
@dataclass
class Segment:
    text: str
    origin: str        # "system" | "user" | "retrieved" | "tool"  — 호출자가 알려준다
    content_type: str  # "prose" | "code" | "structured" | "log" | "unknown" — 검사기가 판정 (§2.6.2)
```

**`origin`과 `content_type`은 직교한다.** `origin`은 "누가 넣었나"(A-INJ-01 vs A-INJ-02 구분에 필수), `content_type`은 "무엇인가"(§2.6 정책 전환). RAG로 가져온 코드도, 사용자가 붙여넣은 로그도 있다.

`Inspector().check(text)` 단일 문자열 호출은 `[Segment(text, origin="user", content_type=자동판정)]`의 편의 래퍼다.

#### 3.2.2 출력

```python
@dataclass
class Finding:
    code: str              # "L-KR-01" | "A-INJ-01" ...
    span: tuple[int, int]  # 원문 문자 오프셋 (§3.2.4 역매핑 적용 후)
    confidence: float      # §3.2.3 산출 규칙
    layer: str             # "L0" | "L1" | "L2"
    rule: str              # "rrn_checksum" | "ner" | "classifier" | ...
    segment_idx: int       # 어느 세그먼트에서 나왔나
    evasion: list[str]     # ["A-KO-01", ...] — 은닉 코드 (§2.2.4)
    normalized_only: bool  # 정규화본에서만 발견 = 은닉 시도
    decoded_from: tuple[int, int] | None  # base64 덩어리 스팬 (§3.2.4 예외)
    rule_version: str      # 규칙셋 버전 — 회귀 추적용

@dataclass
class CheckResult:
    verdict: str                  # "allow" | "mask" | "warn" | "block"
    leaks: list[Finding]
    attacks: list[Finding]
    masked_text: str | None       # verdict=="mask"
    vault: Vault | None           # 응답 복원용 (§3.3)
    normalization_delta: dict     # §3.2.5 스키마
    content_types: list[str]      # 세그먼트별 판정 타입
    degraded: bool                # 검사 일부가 실패했는가 (§3.6)
    latency_ms: dict              # 계층별 분해
```

#### 3.2.3 L0/L1 병합과 confidence 산출

**같은 스팬을 L0·L1이 둘 다 잡을 수 있다.** 규칙을 못박는다.

| 상황 | 채택 | confidence |
|---|---|---|
| L0 체크섬 통과 (RRN·FRN·BIZNO·CORPNO·CARD) | **L0** | **1.0** |
| L0 형식 일치 + 체크섬 없는 엔티티 (여권·면허·계좌·건보·전화·이메일·IP) | L0 | 0.8 |
| L0 형식 일치 + **체크섬 실패** | **탐지 아님** — 오탐 억제 | — |
| L0 형식 일치 + 체크섬 실패 + **L1도 탐지** | L1 채택, `rule="ner_over_checksum_fail"` | L1 확률 × 0.7 |
| L0·L1 스팬 완전 일치 | L0 | max(L0, L1) |
| **L1만 탐지** (L0 미발동) | L1 | L1 확률 × 0.9 |
| 스팬 부분 중첩 | **긴 쪽 채택**, 짧은 쪽 폐기 | 채택된 쪽 |
| L2가 재판정 | L2 | L2 판정으로 덮어씀 |

**이 표가 합성 코퍼스의 표기 변형 비중(§5.3.2)을 결정한다.** L1이 "L0가 놓치는 변형"을 학습해야 앙상블이 성립한다.

#### 3.2.4 ★ 정규화본 스팬 → 원문 스팬 역매핑

**설계 중심 아이디어(§2.3)를 구현하는 유일한 알고리즘이다.** 정규화 7단계가 전부 길이를 바꾸므로 역매핑이 없으면 `Finding.span`을 채울 수 없다.

각 단계가 `(출력, 출력i→입력i 맵)`을 함께 낸다. 체인 끝에서 맵을 합성하면 정규화본의 임의 위치에서 원문 위치를 얻는다.

| 단계 유형 | 맵 |
|---|---|
| 삭제 (제로위드·태그문자) | 남은 문자의 원 인덱스만 기록 |
| 1:1 치환 (homoglyph·한자·NFKC 대부분) | 항등 맵 |
| N:1 축약 (자모 조합) | 출력 인덱스가 **첫 자모의 입력 인덱스**를 가리킴 |
| 공백 정규화 | 삭제와 동일 |

```python
def compose(maps):                      # 여러 단계 맵 합성
    cur = maps[0]
    for nxt in maps[1:]:
        cur = [cur[j] for j in nxt]
    return cur

def to_source_span(norm_span, omap, src_len):
    a, b = norm_span
    return (omap[a], omap[b] if b < len(omap) else src_len)
```

**base64 디코드는 예외다.** 디코드 결과 안에서 발견한 것은 **원문에 대응 오프셋이 없다.**
→ `span`은 **base64 덩어리 전체**를 가리키고, `decoded_from`에 그 덩어리 스팬을 넣는다. 마스킹은 덩어리 전체를 치환한다.

프로토타입으로 검증했다 — 제로위드·homoglyph·자모분해·복합 4케이스에서 **역매핑으로 잘라낸 원문이 정규화하면 발견값과 일치**(4/4). 재현: [offset_probe.py](offset_probe.py)

#### 3.2.5 정규화 델타 스키마

§2.3의 정규화 7단계에 대응한다. **8차원인 이유**: ② 단계가 제로위드 제거와 태그 문자 제거 둘을 하는데, **둘 다 고정밀이지만 별도로 세는 편이 진단에 유리**하다. 나머지 6단계는 1:1이다. **고정밀/저정밀 구분이 신호 여부를 가른다**(부록 A.2).

```python
{
  "nfkc": int,           # 저정밀 — 변경된 문자 수
  "zero_width": int,     # ★고정밀 — 제거된 문자 수
  "tag_chars": int,      # ★고정밀 — 제거된 태그 문자 수
  "homoglyph": int,      # ★고정밀 — 치환된 문자 수
  "jamo_composed": int,  # ★고정밀 — 조합된 음절 수 (길이 차가 아니라 직접 카운트)
  "hanja": int,          # 저정밀 — 치환된 문자 수
  "space": int,          # 저정밀 — 제거된 공백 수
  "b64_decoded": int,    # 저정밀 — 디코드된 덩어리 수
}
```

**고정밀 4종 중 하나라도 > 0이면 은닉 시도 신호**다. 저정밀은 신호가 아니라 재검사 수단이다. 이 8차원이 R2의 보조 feature가 된다(§6.2).

#### 3.2.6 판정 4모드와 집계

| 모드 | 동작 |
|---|---|
| `allow` | 통과 |
| `mask` | 토큰 치환 후 통과. 응답에서 복원 |
| `warn` | 통과시키되 경고 반환. 앱이 결정 |
| `block` | 거부. 사유와 규칙 ID 반환 |

**집계 규칙**: 여러 Finding이 있으면 **최대 심각도를 채택**한다 (`block` > `warn` > `mask` > `allow`). 동률이면 confidence가 높은 쪽의 사유를 대표로 보고한다.

**코드별 기본 판정**

| 코드군 | 기본 | 근거 |
|---|---|---|
| **L-KR-01 주민등록번호 · L-KR-02 외국인등록번호** | **`block`** | 개인정보보호법상 **법적 근거 없는 처리가 동의 여부와 무관하게 금지**되는 고유식별정보. 마스킹으로도 외부 API에 보내지 않는다 |
| L-KR-03~08, L-CM-01~04, L-CT-01~03 | `mask` | 기본값 |
| L-SEC-01~04 (키·개인키·DB문자열) | **`block`** | 유출 시 즉시 악용 가능 |
| L-SEC-05 (일반 고엔트로피) | `warn` | 오탐 가능성 |
| **L-DOC-01 기밀 표식** | **`warn`** | 오탐 비용이 UX를 크게 해친다 (§2.5) |
| A-* 공격 전체 | `warn` | 검사기는 판정만 하고 앱이 결정한다 |

**기본값이 `block`이 아니라 `mask`인 이유**: 과탐은 곧 우회(사용자가 검사기를 꺼버림)를 부른다.

정책 YAML로 코드별 오버라이드가 가능하다(§3.7).

### 3.3 마스킹과 복원

```
원문   "김철수(900101-1234567) 고객 문의"
  │ mask
  ▼
마스킹 "<PERSON_1>(<KR_RRN_1>) 고객 문의"   → LLM API로 전송
  │
  ▼ 응답 "<PERSON_1>님의 문의를 확인했습니다"
  │ restore
  ▼
최종   "김철수님의 문의를 확인했습니다"        → 사용자에게
```

```python
@dataclass
class Vault:
    scope: str                    # "task" | "session" — ★ 요청 스코프가 아니다
    entries: dict[str, str]       # "<KR_RRN_1>" → "900101-1234567"
    counters: dict[str, int]      # 태그별 다음 일련번호
```

⚠️ **볼트 스코프는 요청 단위가 아니라 태스크/세션 단위다.** 요청마다 카운터를 초기화하면 **연속된 두 고객 조회가 둘 다 `<KR_RRN_1>`을 받아** 복원 시 다른 사람의 주민등록번호가 돌아온다. 앞선 설계의 결함이었고 코드로 재현해 확인했다.

**같은 값은 같은 토큰**을 받아야 한다(coreference) — 같은 대화 안에서 `김철수`가 두 번 나오면 둘 다 `<PERSON_1>`이어야 LLM이 동일인으로 이해한다.

**복원은 반드시 앱으로 돌아가는 경로에 있어야 한다.** 사용자는 자기가 입력한 값을 볼 권한이 있다. 마스킹은 외부 API에 대한 것이지 사용자에 대한 것이 아니다.

**조사 결합 처리** — 여기가 진짜 문제가 사는 자리다.

| 상황 | 문제 | 대응 |
|---|---|---|
| 단순 토큰화 | `홍길동이` → `<PERSON_1>이` → 복원 `홍길동이`. **문제없다** | — |
| **LLM이 조사를 새로 생성** | 모델이 토큰 종성을 몰라 `<PERSON_1>가`를 쓴다 → 복원 `홍길동가` (비문) | **복원 시 앞 음절 종성을 보고 이형태 교정** (이/가, 을/를, 은/는, 과/와, 으로/로) |
| 토큰 변형 | 모델이 `<person_1>`, `< PERSON_1 >`로 변형 | 대소문자·공백 관용 매칭. **허용 범위를 테스트로 고정**(과하면 오복원) |

**형태소 분석기는 쓰지 않는다.** kiwipiepy가 LGPL이라 라이선스 조합이 복잡해지고, 조사 이형태 교정은 **앞 음절의 종성 유무만 보면 되므로 순수 규칙으로 충분하다**. 한글 유니코드에서 종성은 `(코드 - 0xAC00) % 28`로 즉시 나온다.

**주의: 조사 교정을 텍스트 전체에 걸면 안 된다.** `이케아→이케야` 같은 훼손이 위험 케이스 10건 중 3건에서 발생했다. **복원된 토큰 바로 뒤에만 적용하고 호격 `아/야`를 제외**하면 복원 7/7·훼손 0/6이다. 상세는 [부록 A.4](#a4-조사-교정의-적용-범위).

```

**의존 방향은 한 방향이다**: `api` → `policy` → `detect` → `segment`/`normalize`/`mask`. 정규화는 아무것도 의존하지 않는 최하층이고, 그래서 단독으로 테스트하고 단독으로 가치가 있다.

**`normalize`가 최하층인 것이 설계의 요점이다.** 우회 방어가 모델이 아니라 여기 있으므로, 학습이 하나도 안 끝나도 L0만으로 제품이 성립한다.

### 3.5 하드웨어 프로파일

성능을 보고할 때 **어느 프로파일에서 쟀는지 반드시 명시한다.**

| 프로파일 | 사양 | 구성 |
|---|---|---|
| **P0** | 아무 노트북 | L0만. 모델 없음, 메모리 ~0 |
| **P1** | 노트북 CPU, RAM 8GB | L0 + L1 (ONNX INT8, ~0.15GB). **L2 없음** |
| **P2** | 노트북 CPU, RAM 16GB | P1 + **L2 2종** (`thorough`, ~4.9~5.5GB — §6.4.4) |
| **P-T** | RTX 4090 (RunPod) | 학습 전용, 런타임과 무관 |

⚠️ **P1(8GB)에는 L2를 두지 않는다.** L2-fast 단독조차 ~2.0~2.2GB이고 OS·사용자 앱과 공존할 여유가 없다. **P1에 대한 L2 검증 항목을 만들지 않는다** — 검산은 §6.4.4에 있다.

**기준 머신을 P2로 선언한다.** 지연 수치는 전부 P2 기준이고, 다른 프로파일 수치를 보고할 때는 그 자리에 프로파일을 명시한다(평가 원칙 5).


### 3.6 실패 정책 — fail 방향을 못박는다

보안 도구는 실패 시 동작을 선언해야 한다. **원칙: 검사 실패는 통과시키되 `degraded=true`를 반환한다.** 검사기가 앱을 멈추면 사용자가 꺼버리고, 그러면 아무것도 못 막는다.

| 실패 | 동작 | verdict |
|---|---|---|
| **L0 규칙 예외** | **차단** — L0는 결정적이라 실패가 곧 버그 | `block` + `degraded` |
| L1 모델 로드 실패 | L0 결과만으로 판정 | 그대로 + `degraded` |
| L1 ONNX 추론 예외 | 해당 세그먼트 L1 생략 | 그대로 + `degraded` |
| L1 지연 예산 초과 | 타임아웃 후 L0 결과 채택 | 그대로 + `degraded` |
| L2 출력 파싱 실패 | L1 결과 유지 | 최소 `warn` + `degraded` |
| 입력 인코딩 오류 (서로게이트 등) | 해당 세그먼트 제외 | `warn` + `degraded` |
| 초장문 (상한 초과) | 청크 분할 후 검사. 청크 수 상한 초과 시 | `warn` + `degraded` |
| **타입 감지 불확실** | `prose`(가장 엄격) 폴백 | 정상 진행 |

**`degraded=true`는 호출자가 반드시 볼 수 있어야 한다.** 조용한 성능 저하가 구 프로젝트에서 문제였다.

## 4. 모델

브리프가 *"use on-device model for program (prefer to use google model (ex: gemma4)) (and check the license for use)"* 를 요구한다. **조사 결과 이 두 요구가 서로 충돌한다.** 그 충돌을 먼저 드러낸 뒤 선정한다.

### 4.1 ★ 핵심 긴장 — Apache 2.0을 원하면 Gemma 4뿐인데, Gemma 4는 분류를 못 한다

**Gemma 4로 토큰 분류(NER)는 불가능하다.** transformers의 `gemma4` 모듈에 분류 헤드가 하나도 없다 — 존재하는 클래스는 `Gemma4ForCausalLM`·`Gemma4ForConditionalGeneration` 계열뿐이다. `MODEL_FOR_TOKEN_CLASSIFICATION_MAPPING_NAMES`에 등록된 Gemma 계열은 `gemma`·`gemma2`·`t5gemma`·`t5gemma2`이고 **gemma3도 gemma4도 없다.** 추가 PR(#45438)은 **OPEN + ON HOLD**이며 그나마 SequenceClassification만 다루고 TokenClassification은 범위 밖이다.

그래서 Gemma 계열에서 분류를 하려면 **Gemma 3 기반 파생**으로 내려가야 하는데, **그 순간 Apache 2.0을 잃는다.**

| 후보 | Google | 라이선스 | 토큰 분류 | 시퀀스 분류 | CPU 적합성 |
|---|:-:|---|---|---|---|
| **Gemma 4 E2B** | ✅ | **Apache 2.0** | ❌ **헤드 없음** | ❌ 없음(PR 보류) | ❌ 유효 2.3B이나 **임베딩 포함 5.1B**, 인과 마스크 |
| **EmbeddingGemma 308M** | ✅ | **Gemma ToU** | ⚠️ 직접 배선(~20줄) | ✅ `Gemma3TextForSequenceClassification` 그대로 로드 | ✅ **300M, 진짜 양방향** (`use_bidirectional_attention: true`) |
| **T5Gemma 2 270m-270m** | ✅ | **Gemma ToU · gated** | ✅ **공식 지원** | ✅ | ⚠️ 이름은 270m-270m이지만 **실측 파라미터는 ~0.79B** — 비전 타워를 포함한 멀티모달 체크포인트다. 그리고 v2는 인코더 전용 토글이 없어 **enc+dec 항상 실행**. 둘이 겹쳐 A.X 대비 **연산량 ~5.4배**(§6.1) |
| `skt/A.X-Encoder-base` | ❌ | **Apache 2.0** | ✅ | ✅ | ✅ 0.1B, 16k, 전량 활성 |

**Gemma ToU를 받아들인다는 것의 실제 의미**: 재배포 시 사용 제한 조항 전파 의무, Prohibited Use Policy 참조 편입(Google이 임의 갱신 가능), 해지 조항. OSI 승인 오픈소스가 아니다. 브리프가 *"check the license for use"* 를 요구한 것이 정확히 이 지점이다.

부가 사실: **ShieldGemma에 Gemma 4 기반 후속이 없고**(최신이 2025-03 Gemma 3 기반 이미지 전용), **Gemma 4의 공식 한국어 벤치마크 수치가 단 하나도 없다**(기술보고서 arXiv:2607.02770에 KMMLU/KLUE/Ko-NER 전무). 그리고 **Gemma 토큰 분류 생태계가 사실상 존재하지 않는다** — HF 전체에 11개, 다운로드 0~33회.

### 4.2 선정 원칙 — 태스크 성격에 따라 계열을 나눈다

브리프의 *"사용 목적에 따라 BERT도 사용 가능"* 이라는 완화가 §4.1의 긴장을 푼다. **모델 계열을 선호도가 아니라 태스크 성격으로 정한다.**

| 태스크 성격 | 모델 계열 | 이유 |
|---|---|---|
| **판별 (토큰 분류·시퀀스 분류)** | **BERT 계열 인코더** | **양방향 어텐션**이 필수다. NER은 뒤 문맥을 봐야 경계를 정한다(`이상무가` — 인명인가 직책인가). 디코더의 인과 마스크는 구조적으로 불리하다. 그리고 소형(0.1~0.3B)이라 CPU에서 예측 가능하다 |
| **생성·판정 (자유 서술)** | **Gemma 4** | 정책을 프롬프트로 주고 판정시키는 자리. Apache 2.0이고 Google 모델이라 브리프 요건을 정면으로 충족한다 |
| **교사 (의사라벨 생성)** | **Gemma 4 + Kanana 병행** | 생성형이므로 Gemma의 자리. 두 교사의 합의를 라벨로 |

이 원칙이 §4.1의 충돌을 해소한다. **Gemma 4가 분류 헤드가 없는 것은 결함이 아니라 설계 의도**다 — 생성 모델이니까. 판별에는 판별용 아키텍처를 쓰고, Gemma는 생성이 필요한 자리에 쓴다.

**따라서 L1 백본의 기본값은 `skt/A.X-Encoder-base`(한국어 ModernBERT, Apache 2.0, 0.1B)다.** 다만 Gemma 계열 인코더 파생이 실제로 더 나은지는 W1에 실측으로 확인한다 — 근거 없이 배제하지 않는다.

| 역할 | 채택 | 라이선스 | 근거 |
|---|---|---|---|
| **L1-PII (NER)** | **`skt/A.X-Encoder-base`** (기본값) — 대안으로 EmbeddingGemma 300m / T5Gemma 2 270m-270m(**실측 ~0.79B**)를 W1에 실측 비교 | **Apache 2.0** | 한국어 ModernBERT, 16k 컨텍스트, 양방향, 전량 활성이라 CPU 지연이 예측 가능 |
| **L1-ATK (공격 분류)** | **`skt/A.X-Encoder-base`** (같은 백본, 다른 헤드) — 대안 EmbeddingGemma 308M(`Gemma3TextForSequenceClassification` 그대로 로드) | Apache 2.0 / Gemma ToU | 백본을 공유하면 메모리가 절반이다. 참조 구현 `robustintelligence/pi-t5gemma-2-1b-v5.0`(인코더 전용 + mean-pooling + 선형 헤드, FPR 0.5%에서 F1 89)의 레시피를 이식 |
| **L2-fast (선택)** | **`kanana-safeguard-prompt-2.1b`** — 상시 상주(`ttl:0`) | Apache 2.0 | 공격 의도 전담. 단일 토큰 디코드라 밀리초급. **P 0.968**이라 `UNSAFE`만 신뢰하고 `SAFE`는 확정 근거로 쓰지 않는다(§7.1.2) |
| **L2-judge (선택)** | **`Qwen3Guard-Gen-4B`**(기본) / `FrameByFrame/guardrail-korean-gemma-4-E2B`(대안) — 온디맨드(`ttl:60~120`) | Apache 2.0 / Gemma ToU | PII 문맥·기밀·플레이스홀더 판정. Qwen3Guard는 RTP-LX 한국어 **F1 85.7**(독립 벤치)에 `Controversial` 심각도가 애매 케이스 전용이라 L2에 맞는다. 대안은 **자체 홀드아웃** F1 0.925로 독립 검증이 없다. 상세 §6.4 |
| **R2 교사** | `kanana-safeguard-prompt-2.1b` + **Gemma 4 E2B 병행** | Apache 2.0 | 두 교사의 **합의(agreement)를 라벨로** 쓰면 의사라벨 품질이 올라간다. Gemma 4는 생성형이므로 교사 자리가 자연스럽다 |

#### 4.2.1 W1 백본 실측 비교 — 기본값을 뒤집을 근거가 있는가

기본값은 A.X-Encoder지만, **Gemma 계열이 더 나은지를 근거 없이 배제하지 않는다.** 세 후보를 같은 조건에서 잰다.

| 기준 | 측정 방법 |
|---|---|
| ① CPU 지연 (ONNX INT8, 128/256/512 토큰) | 목표 `interactive` 예산 안 |
| ② 한국어 NER F1 (KLUE-NER 파일럿 + 합성 셋) | 동일 데이터·동일 학습 설정 |
| ③ 메모리 (RSS) | P1 프로파일(8GB) 수용 여부 |
| ④ **라이선스** | Apache 2.0(A.X-Encoder) vs Gemma ToU(Gemma 계열) |

**①②③에서 Gemma 계열이 유의하게 앞서면 Gemma ToU를 받아들이고 기본값을 뒤집는다. 대등하거나 밀리면 Apache 2.0인 A.X-Encoder를 유지한다.** 어느 쪽이든 **판단 근거를 수치로 공개한다.**

**백본 공유가 기본이다.** L1-PII와 L1-ATK가 같은 인코더에 헤드만 둘을 붙이면 메모리가 절반이고 로딩도 한 번이다. 두 태스크가 서로 다른 백본을 요구할 만큼 성능 차가 나는지도 ②에서 함께 본다.

⚠️ **T5Gemma 2의 함정**: v1은 `is_encoder_decoder=False`로 인코더 전용이 되지만 **v2에는 그 토글이 없다.** `T5Gemma2ForTokenClassification.forward()`가 항상 인코더+디코더를 다 돌리고 디코더의 `last_hidden_state`에 헤드를 붙인다 → CPU 연산량 약 2배. 공식 지원이라는 장점이 이 비용을 상쇄하는지가 ①의 관건이다.

### 4.3 기각한 후보와 사유

| 대상 | 사유 |
|---|---|
| **Gemma 4를 L1 백본으로** | 분류 헤드 없음(PR 보류 중), 임베딩 포함 5.1B, 인과 마스크. **결함이 아니라 생성 모델이기 때문이다** — 생성형 자리(L2·교사)에 쓴다 |
| **`openai/privacy-filter`** | **실측으로 탈락.** M2 MacBook MPS 중앙값 958ms / p90 1,725ms, CPU는 2~3배 느림. "활성 50M"이 CPU 지연으로 번역되지 않는다 — top-4-of-128 라우팅이 토큰마다 메모리 대역폭에 묶이고 1.5B가 전부 상주한다 |
| `klue/roberta-*` | CC-BY-SA-4.0. ShareAlike가 학습 가중치에 전파되는지 불확실 → **평가 비교용으로만** |
| Llama Guard / Prompt Guard | 한국어 공식 미지원 + Llama Community License |
| ShieldGemma | 영어 전용(1) / 이미지 전용(2). **Gemma 4 기반 후속 없음** |
| 클라우드 API (Model Armor, Cloud DLP) | **프롬프트가 외부로 나간다.** 제품 논리와 정면 모순 |

> **`openai/privacy-filter` 기각은 앞선 설계의 오류를 바로잡은 것이다.** "active 50M이니 CPU 실용 가능"이라 추론했는데 틀렸다.

### 4.4 ONNX INT8 — 선택이 아니라 필수

CPU에서 0.1B 인코더를 512토큰으로 돌리면 PyTorch fp32 기준 150~400ms다. ONNX Runtime INT8로 50~150ms까지 내려간다. **L1 목표 지연은 양자화를 전제로만 성립한다.**

그래서 **W1 첫날에 §4.2.1의 세 후보를 전부 ONNX INT8로 내보내 실제 노트북에서 128/256/512 토큰 지연을 측정한다.** 반나절이면 되고, 이 숫자가 아키텍처를 확정한다. 앞선 계획은 이 답이 3주차에 나오게 설계돼 있었는데, 그때는 이미 그 가정 위에 2주를 지은 뒤다.

**입력 길이 상한을 둔다.** 긴 프롬프트는 청크로 나눠 검사하고, 청크 경계에 걸친 엔티티는 오버랩 윈도우로 처리한다.

| **`smilegate-ai/korean_unsmile`** | **CC-BY-NC-ND-4.0.** 비상업 + 파생물 금지 둘 다. 학습 모델이 파생물로 해석될 여지가 크다 |
| **AI-Hub 전체** | 제3자 제공 금지, 상업적 이용은 수행기관 별도 협의, 국외 소재 시 NIA 별도 합의. **서면 승인 전까지 파이프라인 금지** |

| KOLD, LoL 리스트, AssurAI | 라이선스 불명 / Restricted |

**제외 목록을 학습 파이프라인에 하드코딩하고 검증 스크립트로 강제한다.** 실수로 섞이면 상용 배포가 막힌다.

⚠️ **검증 스크립트는 이 문서의 라이선스 표기를 읽지 않는다.** 문서는 조사 시점의 스냅샷이고 데이터셋 카드는 바뀐다 — 실제로 `PolyGuardPrompts`를 **ODC-BY로 잘못 적어 뒀다가 CC-BY-4.0으로 정정**했다. 문서 문자열을 진실의 원천으로 삼으면 그 오류가 그대로 통과한다.

→ 스크립트는 **HuggingFace API를 런타임에 조회**해 각 데이터셋의 현재 라이선스 태그를 읽고, **허용 목록(Apache-2.0 / MIT / CC-BY-4.0 / CC0)에 없으면 실패**시킨다. 태그가 없거나 조회에 실패하면 **통과가 아니라 실패**로 처리한다(fail-closed).

### 5.3 자체 합성 코퍼스 — 실질 주력

공개 데이터로 커버되지 않는 부분이 크다. 한국 고유 식별자와 한국어 우회 벡터는 공개 자산이 없다. 그리고 **평가에는 합성이 유리하다** — 어려운 케이스를 통제된 비율로 만들 수 있다.

#### 5.3.1 규모

| 항목 | 목표 | 근거 |
|---|---|---|
| **템플릿 수** | **1,000개 이상** | 90/5/5 템플릿 분할 시 test 50개 확보. 200개면 test 10개로 판별력이 없다 |
| 총 인스턴스 | **50,000** | 템플릿당 평균 50 |
| **태그별 최소** | **각 1,500** | **정의: 양성 라벨 출현 횟수(span 개수).** 음성 유형(무효 체크섬·형식 유사)은 집계 제외 |

**산술 검증**: 앙상블 11종 × 1,500 = 16,500 출현이 유효 체크섬 15,000 인스턴스 안에 → 인스턴스당 1.10개(가능). L1 전담 3종 × 1,500 = 4,500이 문맥 의존 7,500 안에 → 0.60개(가능).

#### 5.3.2 유형 비율과 표기 변형

| 유형 | 비율 | 내용 |
|---|---|---|
| 유효 체크섬 PII | 30% | 8종 식별자 + 국제 3종, 체크섬 통과 |
| **무효 체크섬** | 20% | 형식은 맞지만 체크섬 실패 → L0가 걸러야 함 |
| **형식 유사 비-PII** | 25% | 주문번호 `2026-0803-1234`, 사번 `EMP-900101`, 제품 시리얼, 송장번호 → **오탐 측정의 핵심** |
| 문맥 의존 PII | 15% | 조사 결합 성명, 도로명·지번 혼합 주소, 조직 내부 식별자 |
| 완전 무해 | 10% | PII 없는 일반 업무 문장 |

**"유효 체크섬 PII" 30% 안의 표기 변형** — §3.2.3의 앙상블 역할을 데이터로 뒷받침한다.

| 표기 | 비중 | 예 | 누가 잡아야 하나 |
|---|---|---|---|
| 표준 구분자 | 50% | `900101-1234567` | L0 |
| **공백 구분자** | 15% | `900101 1234567` | **L1** |
| 구분자 없음 | 15% | `9001011234567` | L0(정규식 확장) 또는 L1 |
| **줄바꿈·괄호 삽입** | 10% | `900101-\n1234567` | **L1** |
| **자연어 표기** | 10% | `구공공일공일에 다시 일이삼사...` | **L1 전담** |

#### 5.3.3 content_type 축 (§2.6)

유형 비율과 **교차**한다.

| content_type | 비중 | 특징 |
|---|---|---|
| `prose` | 60% | 기본 |
| **`code`** | 15% | 변수명이 PII처럼 보이는 케이스 **집중 배치**, 진짜 PII가 문자열 리터럴에 있는 케이스 |
| **`structured`** | 15% | JSON/YAML. 키-값 양쪽에 PII 형식 문자열 |
| `log` | 5% | IP·타임스탬프·UUID 밀집 정상 로그 |
| **`mixed`** | 5% | 산문 + 코드 블록. **세그먼트 자동 분할 검증용** |

**`code`·`structured`·`log`의 과반이 "정상"(PII 없음)이어야 한다** — 오탐 측정의 핵심이다.

#### 5.3.4 파일 스키마

```jsonc
{
  "id": "syn-000001",
  "template_id": "tpl-0042",        // ★ 분할 키 (§6.3)
  "text": "김철수 고객님(900101-1234567)의 환불 건입니다.",
  "spans": [
    {"start": 0, "end": 3, "label": "PERSON"},
    {"start": 9, "end": 23, "label": "KR_RRN"}
  ],
  "meta": {
    "type": "valid_checksum",       // §5.3.2 5유형
    "notation": "standard",         // §5.3.2 표기 변형
    "content_type": "prose",        // §5.3.3
    "synthetic": true               // 실제 개인정보 아님 보증
  }
}
```

**오프셋은 문자 단위**이고 `text`의 파이썬 슬라이싱과 정확히 일치해야 한다. 생성기가 검증한다.

#### 5.3.5 슬롯 값 소스와 라이선스

| 슬롯 | 소스 | 라이선스 |
|---|---|---|
| 한국 성명 | **성씨 빈도표(공공데이터) + 음절 조합 생성** | 실제 인명 목록 미사용 |
| 도로명 주소 | **도로명주소 형식 규칙으로 합성** (시도·시군구 사전 + 임의 번지) | 실주소 미사용 |
| 주민·외국인등록번호 | 체크섬 생성기 + **존재 불가 생년월일**(`991332`) | 자체 |
| 사업자·법인번호 | 체크섬 생성기 | 자체 |
| 카드 | Luhn 생성기 + 테스트 BIN(`4242…`) | 자체 |
| 계좌·여권·면허·건보 | 형식 규칙 생성기 | 자체 |
| 업무 문장 골격 | **Gemini API로 다양화** (§7.4 ③) | 합성값만 조립, PII는 넣지 않음 |

> **절대 원칙: 실제 개인정보는 어떤 경로로도 저장소에 넣지 않는다.** 검증 스크립트([checksum_probe.py](checksum_probe.py))가 이 방식을 쓴다.

#### 5.3.6 공격 코퍼스

의도 3종(NONE 제외) × 은닉 7종 조합.

| 항목 | 목표 |
|---|---|
| 기본 공격 텍스트 | **의도별 200 이상 → 3종 × 200 = 600** |
| 은닉 적용 | (3 의도 × 8 은닉상태[없음 포함]) = **24 조합, 조합당 최소 50 → 1,200** |
| **benign** | **1,200 이상 (공격과 동수 이상).** 존댓말 업무 요청, 정상 한자 병기, 들여쓰기 문서 포함 |

benign에 부록 A.2의 오탐원(들여쓰기 문서)과 A.5의 오탐원("대외비인데")을 **반드시 넣는다.**

**뮤테이터가 판정 앵커를 파괴하는 조합은 제외하고 사유를 데이터 카드에 기록한다.**

⚠️ 공격 코퍼스는 PII 코퍼스 50,000과 **별도 풀**이며 템플릿 1,000에 포함되지 않는다.

### 5.4 테스트 데이터 — 네 겹

| 겹 | 규모 | 구성 | 무엇을 재는가 |
|---|---|---|---|
| **T1 템플릿 홀드아웃** | 2,500 (템플릿 50개) | 학습에 안 쓰인 템플릿에서 생성. **태그별 최소 100** | 패턴 일반화 (H1) |
| **T2 외부 held-out** | 1,000 | PolyGuardPrompts 한국어 + KLUE-NER(평가 전용) | 자작 편향 견제 |
| **T3 수동 골드셋** | **200** | 실제 업무 문서 스타일을 직접 작성·라벨링 | **최종 KPI** |
| **T4 우회 벡터 평가셋** | **2,800** | 3 의도 × 7 은닉 = 21셀 × 100 + 벡터별 benign 7 × 100 | **H2 전용** |

⚠️ **T2의 한계를 명시한다.** KLUE-NER의 태그는 `PS/LC/OG/DT/TI/QT`뿐이라 **한국 고유 8종에 대응하는 태그가 없고**, PolyGuardPrompts는 공격 데이터라 PII 스팬이 없다. 따라서 **한국 고유 식별자 11종에 대한 외부 held-out 증거는 0**이다. "자작 편향 견제"라는 T2의 목적이 정작 자작 비중이 가장 큰 태그에서 작동하지 않는다 — 이것을 한계 절에 그대로 쓴다.

**T4 규모 근거**: 셀당 재현율 ±0.10 신뢰구간을 원하면 셀당 ~100건이 필요하다. `kimchunsik03/KoreanGuardrail`(자모분해·초성체·띄어쓰기 파괴 견고성 벤치마크)을 회귀 테스트로 병용하되, 라이선스와 태그 정합을 W4에 확인한다.

**T3 라벨링 프로토콜** — 1인 라벨링이므로 편향을 인정한다. ① 라벨링 전에 가이드 문서를 먼저 고정 ② 모델 예측을 보지 않고 라벨 ③ 2주 간격 재라벨로 **자기일치도(Cohen's κ) 보고**.

## 6. 학습 방법

### 6.1 R1 — 한국 PII NER

**왜 학습하는가**: L0 규칙이 원리적으로 못 잡는 것이 있다 — 조사가 붙은 한국식 성명(`이상무가` — 인명인가 직책인가), 도로명·지번 혼합 주소, 자연어로 풀어 쓴 번호. 그리고 **어떤 공개 모델도 한국 고유 식별자 태그를 갖고 있지 않다.**

**태그 셋** — §2.1의 코드와 대응하고, §3.2.3의 병합 표가 각 태그의 역할을 정한다.

| 부류 | 태그 | 역할 |
|---|---|---|
| **앙상블 11종** (L0도 잡음) | `KR_RRN` `KR_FRN` `KR_PASSPORT` `KR_DL` `KR_BIZNO` `KR_CORPNO` `KR_NHI` `KR_ACCOUNT` `CARD` `PHONE` `EMAIL` | L0가 놓친 **변형 표기**를 보강 (§5.3.2의 공백·줄바꿈·자연어 표기 40%) |
| **L1 전담 3종** | `PERSON` `ADDRESS` `ORG_ID` | L0가 원리적으로 못 잡음 |

**= 14종 × BIO(B-, I-) + O = 29 라벨.**

**설정**

| 항목 | 값 |
|---|---|
| 베이스 | **W1 실측 비교 3종** — `skt/A.X-Encoder-base`(기본값) / `google/embeddinggemma-300m` / `google/t5gemma-2-270m-270m` |
| 헤드 | 토큰 분류 29 라벨 |
| 방식 | **풀 파인튜닝** — 커스텀 태그 셋이라 헤드가 랜덤 초기화. 인코더를 얼리면 성능이 크게 떨어진다 |
| 학습률 | 3e-5, warmup 10% |
| epochs | 5 (early stopping) |
| 배치 / max_len | 32 / 512 |
| 옵티마이저 | AdamW |
| **early stopping** | 감시 지표 **dev character-level recall**, patience 2 |
| **불균형 처리** | O 태그 가중치 하향 또는 focal loss. 희소 태그(여권·건보)는 오버샘플 |
| **seed** | **3개 고정 실행, 평균±표준편차 보고** |
| 데이터 | KDPII(53,778, 태그 매핑 후) + 합성 50,000 (§5.3) |
| **예상 시간** | **~28.5 GPU-h** — 아래 산식 |

**GPU-h 산식** — 백본별 연산량이 다르므로 단순 곱이 아니다.

| 백본 | 파라미터 | 상대 연산량 | 1 seed | × 3 seed |
|---|---|---|---|---|
| `A.X-Encoder-base` | 0.1B | 1× | ~1.0h | 3.0h |
| `embeddinggemma-300m` | 0.30B | ~3.1× | ~3.1h | 9.3h |
| `t5gemma-2-270m-270m` | enc+dec, 실측 ~0.79B | ~5.4× | ~5.4h | 16.2h |
| | | | **합** | **28.5 GPU-h** |

⚠️ 이 값은 4090 기준 추정이다. **W1 첫 실행에서 실측해 갱신한다.** 백본 비교(W1)를 절삭하면 A.X 단독 3.0 GPU-h로 줄어든다.

**한국어 토큰화 함정 — 반드시 지킬 것**

| 함정 | 대응 |
|---|---|
| 조사가 엔티티에 붙는다 (`김철수에게`) | **조사를 엔티티에서 제외.** `<PERSON_1>에게`가 되어야 마스킹 출력이 자연스럽다 |
| 서브워드 ↔ 문자 라벨 정렬이 깨진다 | **`return_offsets_mapping=True`로 문자 오프셋을 진실의 원천으로 삼는다.** BIO 인덱스가 아니라 오프셋으로 스팬 복원 |
| entity-level F1만 보면 오도된다 | **character-level recall을 주 지표로**, entity-level F1 병기. PII는 문자 하나만 새도 유출이다 |

**KDPII 플랜 B** — §8.5 #2가 "주민등록번호가 네이티브 태그로 없을 가능성이 높다"고 본다. **W1 0일차에 실물 태그 분포를 확인**한다.

없으면: KDPII는 `PERSON`/`ADDRESS`/`PHONE`/`EMAIL` 학습에만 쓰고 **한국 고유 8종은 전량 합성**으로 간다. 이때 합성을 **템플릿 1,000 → 1,400개**로 늘린다(인스턴스 50,000 → 70,000). **템플릿당 50은 유지**한다 — 템플릿당 인스턴스를 늘리면 T1(§5.4)이 2,500에서 3,500으로 부풀어 평가셋 규모가 어긋난다.

일정 영향: 합성 생성기 작업 +1.5일. §8.4의 절삭 예산에서 흡수한다.

### 6.2 R2 — 공격 분류기 (distillation)

**왜 distillation인가**: 교사 `kanana-safeguard-prompt-2.1b`는 한국어 인젝션 F1 0.844로 PromptGuard(0.751)·GPT-4o(0.804)를 앞선다. 하지만 2.1B를 노트북에 상주시키면 bf16 4.2GB에 지연도 못 맞춘다. **0.1B로 줄이지 않으면 로컬 실행이 성립하지 않는다.**

#### 6.2.1 학생 출력 구조 — §2.2의 두 축을 그대로 받는다

```
주 헤드 (4-way softmax):  NONE / INJECTION / JAILBREAK / SYSTEM_LEAK
보조 헤드 A (sigmoid):    로마자 표기 우회 여부   (A-KO-03)
보조 헤드 B (sigmoid):    존댓말 사회공학 여부    (A-KO-06)
```

**은닉 축(7종)은 학습하지 않는다** — L0 정규화가 결정적으로 판정한다(§2.2.2). `Finding.code`는 주 헤드가, `Finding.evasion`은 L0가 채운다.

**§2.2 공격 코드 → 출력 매핑 (빈칸 없음)**

| 코드 | 채우는 곳 |
|---|---|
| A-INJ-01 / A-INJ-02 | 주 헤드 `INJECTION` + `Segment.origin`으로 01/02 구분 |
| A-JB-01 / A-JB-02 | 주 헤드 `JAILBREAK` |
| A-LEAK-01 | 주 헤드 `SYSTEM_LEAK` |
| A-ENC-01/02/03, A-KO-01/04/05, A-MISC-01 | **L0 은닉 축** → `Finding.evasion` |
| A-KO-02 초성체 | L0 은닉(자모) 또는 보조 신호 |
| A-KO-03 로마자 | **보조 헤드 A** |
| A-KO-06 존댓말 | **보조 헤드 B** |

#### 6.2.2 교사 2종 — 왜 하나로는 안 되는가

`kanana-safeguard-prompt-2.1b`의 출력은 `<SAFE>` / `<UNSAFE-A1>`(인젝션) / `<UNSAFE-A2>`(프롬프트 리킹) **셋뿐이라 `JAILBREAK`에 대응하는 출력이 없다.** 교사 하나로는 4-way를 못 채운다.

```
1. 무라벨 한국어 프롬프트 수집
   PolyGuardPrompts 한국어(CC-BY-4.0) + deepset 번역 + 자체 합성(§5.3.6) + 은닉 변형

2. 교사 2종 병행 라벨링 (GPU)
   ① kanana-safeguard-prompt-2.1b  → SAFE / A1 / A2   (단일 토큰 + 로짓)
   ② Gemma 4 E2B                   → 정책 프롬프트로 4-way 판정 (생성형)

3. 라벨 확정 규칙
   - 두 교사 합의            → 채택
   - 불일치                  → ★ 학습에서 제외하고 별도 파일로 적재 (사람 검토 큐)
   - kanana에 없는 JAILBREAK → Gemma 단독 판정 + 규칙 힌트(DAN·역할극 패턴)로 채택
   - 보조 헤드 A·B 라벨      → 뮤테이터가 생성 시점에 안다 (교사 불필요)

4. 학생 학습 (백본은 R1과 동일 — 헤드만 다름)
   주 헤드: 손실 = α·CE + (1-α)·KL(kanana 소프트), T=2.0, α=0.5
   ★ Gemma 단독 라벨 구간은 소프트 로짓이 없으므로 CE만
   ★ 보조 헤드 A·B: CE만 (교사 소프트 없음)

5. 정규화 델타 결합 — ★ 명세
   [CLS] 임베딩(768) ⊕ 델타 벡터(8차원, §3.2.5, 규칙별 카운트를 log1p 스케일)
   → 선형층 → 각 헤드
   델타는 L0가 이미 계산한 값이므로 추론 시 추가 비용 0

6. 임계값 캘리브레이션
   dev 셋에서 §7.1의 목표 FPR을 만족하는 최소 임계값 탐색
```

**교사와 학생이 둘 다 Apache 2.0**이고 Gemma 4는 Gemma ToU다 — 학생 가중치 배포 시 Gemma ToU 파생 조항을 확인한다(§8.5).

**시퀀스 분류를 택한 이유**: 교사의 단일 토큰 생성 방식은 임계값 조정이 어렵다. 로짓 기반이어야 **FPR을 목표치에 맞춰 캘리브레이션**할 수 있고, 로컬 도구에서 과탐은 즉시 우회(사용자가 꺼버림)를 부른다.

**단순 압축이 아니다.** 우회 벡터를 학생에게 추가로 가르치므로 **교사가 못 잡는 구간이 생길 수 있다.** 그게 사실인지는 측정 대상이고, 사실이라면 결과의 핵심이 된다.

| 항목 | 값 |
|---|---|
| 방식 | 풀 파인튜닝 (0.1B) |
| 학습률 / epochs / batch | 3e-5 / 5 / 32 |
| seed | 3개, 평균±표준편차 |
| 예상 시간 | 교사 라벨링 **~3 GPU-h** + 학생 ~1 GPU-h × 3 seed = **~6 GPU-h** |
| **ONNX 변환 후 허용 저하** | **주 헤드 재현율 −0.01 이내.** 초과 시 양자화 방식 재검토 |

### 6.3 누수 방지 — 템플릿 단위 분할

합성 데이터는 템플릿에서 인스턴스를 찍어낸다. **행 단위로 나누면 같은 템플릿이 train과 test 양쪽에 들어가고, 모델은 일반화가 아니라 템플릿을 외운다.**

```
잘못:  인스턴스 생성 → 무작위 90/5/5 분할
올바름: 템플릿 ID를 먼저 90/5/5 분할 → 각 분할에서 인스턴스 생성
```

**누수 탐지 4종**

| 방법 | 내용 |
|---|---|
| 템플릿 지문 | PII 스팬을 플레이스홀더로 치환·정규화 후 해시. **train ∩ test = ∅** |
| n-gram 중복 | PII 마스킹 후 5-gram Jaccard |
| MinHash/LSH | 파라미터화로 정확 해시가 못 잡는 근사 중복 |
| **성능 갭 진단** | **행 단위 F1 ≫ 템플릿 단위 F1이면 누수 확정. 두 수치를 모두 보고한다** |

마지막이 가장 강력하고, **두 수치의 차이 자체를 공개하는 것**이 참조 사례들과의 차별점이다.


### 6.4 L2 — 2-모델 하이브리드 (학습 없음, 배선만)

L2는 파인튜닝하지 않는다. **공개 가드 모델을 그대로 쓰고 정책 프롬프트만 갈아 끼운다.**

#### 6.4.1 L2가 판정해야 하는 네 축과 인벤토리

| 축 | 특화 모델 | 크기 | 문제 |
|---|---|---|---|
| (a) PII 문맥 판단 | `kanana-safeguard-siren-8b` — **전체 F1 0.926** (I3 개인정보 카테고리 점수가 아니다) | 8B | **document-level만** — 스팬을 안 준다. 8B는 CPU에서 비싸다 |
| (b) 공격 의도 판단 | **`kanana-safeguard-prompt-2.1b`** F1 0.844 (**P 0.968 / R 0.748**) | 2.1B | ✅ 유일하게 저렴 + 한국어 검증 |
| (c) 기밀 문서 판단 | ❌ **없음** | — | siren I2/I4가 인접하나 "기밀"과 다르다 |
| (d) 시크릿 플레이스홀더 판별 | ❌ **없음** | — | 어떤 공개 가드도 커버하지 않는다 |

**→ 4축 특화 라우팅은 인벤토리가 못 받친다.** (c)(d)는 어차피 범용 모델 + 정책 프롬프트여야 한다.

#### 6.4.2 라우팅을 안 하는 근거

| 근거 | 시사점 |
|---|---|
| **RouteGuard** — 라우터 + 도메인 전문가 5개 | **in-domain 이득 0.2~0.4포인트뿐.** OOD에서만 크다. **지연·메모리 분석이 논문에 없고** 가중치 미공개·다국어 미평가 |
| **ExpGuard** | 범용 가드가 의료 도메인에서 F1 41.2로 붕괴 — 도메인 전환 취약성은 실재한다 |
| MultiTaskGuard / GLiGuard / Opir(<100M) | 단일 멀티태스크·스키마 조건화가 특화 다수를 대체한다는 반대 근거 |
| OpenAI 쿡북(gpt-oss-safeguard) | 권장 구조가 **"소형 고재현율 선필터 → 무거운 정책 판정"** — 우리 L1/L2와 동일 |
| 상용 제품 패턴 (LLM Guard·NeMo·Lakera·Azure) | **작은 전용 검출기 다수 + 큰 judge 1개.** 큰 judge를 여러 개 라우팅하는 선례가 **없다** |

**우리 네 축은 전부 "한국어 프롬프트"라는 같은 분포 = in-domain.** RouteGuard 기준 라우팅 이득이 0.2~0.4포인트인 구간이다. → **라우팅하지 않는다.**

#### 6.4.3 채택 구성

```
L1 (0.1B encoder, 상시 상주)
  └─ 애매(0.4~0.6) ─┐
                    ▼
L2-fast   kanana-safeguard-prompt-2.1b   ttl:0  (상시 상주)
          → 축 (b) 공격 의도 전담. 단일 토큰 디코드라 밀리초급
          → P 0.968 이므로 "UNSAFE면 확정" 신뢰 가능
          → ★ R 0.748 이므로 SAFE는 확정 근거로 쓰지 않는다 (§7.1 주석)

L2-judge  Qwen3Guard-Gen-4B  (기본값)  ttl:60~120  (온디맨드)
          → 축 (a)(c)(d). 축별 정책 프롬프트 4종 전환
```

**judge 후보 비교**

| 후보 | 크기 | 라이선스 | 한국어 근거 | 출력 | 리스크 |
|---|---|---|---|---|---|
| **`Qwen3Guard-Gen-4B`** ★기본 | 4B | **Apache 2.0** | RTP-LX 한국어 **F1 85.7** (독립 벤치) | 9 카테고리 + **3단 심각도**(Safe/Controversial/Unsafe) | 택소노미 고정 — (c)(d)를 직접 못 담아 instruct 경로 필요 |
| `guardrail-korean-gemma-4-E2B` | 총 5.12B (활성 2B) | **Gemma ToU** | **자체 홀드아웃** F1 0.925 (독립 검증 없음) | JSON: span-level PII + reason | GGUF 미확인, 라이선스 |

**Qwen3Guard-4B가 스윗스팟인 이유**: 한국어 F1이 0.6B 77.1 → **4B 85.7**(+8.6) → 8B 86.2(**+0.5**). 4B에서 수확이 끝난다. 그리고 **`Controversial` 심각도 라벨이 애매 케이스 전용**이라 L2 용도에 정확히 맞는다.

→ **W1에 둘 다 GGUF로 변환해 실측 비교하고, 애매하면 Apache 2.0인 Qwen3Guard-4B를 택한다.**

#### 6.4.4 메모리 검산 — ★ P1(8GB)에는 L2를 두지 않는다

| 구성 | 가중치(Q4) | KV(4k / 8k) | compute | 합계 | P1 8GB | P2 16GB |
|---|---|---|---|---|---|---|
| **채택 (2.1B + 4B)** | **~3.8GB** | 0.60 / 1.21 | ~0.5 | **~4.9~5.5GB** | ❌ | ✅ |
| 2.1B + E2B judge | ~4.3GB | 0.60 / 1.21 | ~0.5 | ~5.4~6.0GB | ❌ | ✅ |
| L2-fast 단독 (2.1B) | ~1.4GB | 0.25 / 0.50 | ~0.3 | ~2.0~2.2GB | ⚠️ 가능 | ✅ |

⚠️ **P1(8GB)은 §3.5대로 L0+L1만 돌린다. L2 없음.** 8GB에서 L1(0.1B ONNX INT8, ~0.15GB) + OS + 사용자 앱을 빼면 L2-fast 단독조차 여유가 없다. **P1 L2 검증 항목을 두지 않는다.**

**스왑 페널티(warm)**: 2B↔2B 0.5~1초 / 2B↔8B 1~3초 / **cold 로드 3~10초 — thorough 예산도 초과**한다. 그래서 L2-fast를 상주시킨다.

**런타임 설정** — `llama-swap`은 `ttl`만으로는 부족하다. **`groups` 설정으로 두 모델이 동시 상주 가능함을 명시**해야 한다(기본 동작이 "새 모델 로드 시 기존 언로드"이기 때문). Ollama는 `OLLAMA_MAX_LOADED_MODELS=2` + 모델별 `keep_alive`.

⚠️ **`kanana-safeguard-prompt-2.1b`의 `Q4_K_M` GGUF는 공개돼 있지 않다** (확인된 것은 Q2_K·Q3_K_M). **자체 변환이 W1 작업 항목**이다(§8.1). 변환 후 **Q4 양자화 F1 재측정은 필수** — 단일 토큰 분류기의 양자화 열화에 대한 공개 데이터가 없다.

#### 6.4.5 축 (d)는 모델이 아니라 파이프라인

문헌 합의는 **regex/엔트로피로 후보 생성 → LLM으로 문맥 분류**다. GitHub Secret Scanning이 실제로 이 2단 구조다.

→ **(d) 전용 모델을 두지 않는다.** L2-judge에 짧은 정책 프롬프트 + few-shot으로 붙인다: `YOUR_API_KEY`, `sk_test_...xxxxxxx`, `testkey`, `<your-token-here>`, `${API_KEY}`.

#### 6.4.6 배선 명세

| 항목 | 값 |
|---|---|
| **L2-fast 호출 조건** | L1-ATK confidence **0.4~0.6** 애매 구간 |
| **L2-judge 호출 조건** | ① `thorough` 전건 ② L1-PII 애매 + 문맥 판단 필요 ③ 기밀 표식 위치 가중치 애매 ④ 시크릿 플레이스홀더 후보 |
| 판정 프롬프트 | 축별 4종. Qwen3Guard는 고정 택소노미이므로 (c)(d)에 **별도 instruct 경로가 필요한지 W1에 확인** |
| **출력 파싱 실패** | fail → L1 결과 유지 + 최소 `warn` + `degraded: true` (§3.6) |
| 회귀 평가셋 | `kimchunsik03/KoreanGuardrail` — 자모분해·초성체·띄어쓰기 파괴 견고성. 축 (b) 회귀 테스트 |

## 7. 평가 설계

### 7.1 헤드라인 지표 — 둘

| # | 지표 | 무엇을 증명하는가 |
|---|---|---|
| **H1** | **엔티티별 탐지 F1 + FPR** — 유형 각각, **반드시 같은 표에** | 국내 어느 벤더도 오탐률을 공개하지 않는다 |
| **H2** | **우회 벡터별 공격 탐지율 + 정상 문장 오탐률** | 한국어 우회에 실제로 견디는가 |

**단일 평균은 보고하지 않는다.** 엔티티마다 난이도가 다르고 평균은 그것을 감춘다.

H2의 그룹 변수는 **모델 출력이 아니라 코퍼스 생성 메타데이터**(§5.3.6의 은닉 적용 기록)에서 온다. `Finding.evasion`은 사용자 대면 설명용이지 H2의 근거가 아니다.

#### 7.1.1 ★ 성공 기준 — 수치를 못박는다

**목표값이 없으면 §6.2 6단계(임계값 캘리브레이션)가 착수 불가다.**

| 지표 | 목표 | 검증 셋 | 최소 n | 근거 |
|---|---|---|---|---|
| **L0 체크섬 엔티티** char-recall | ≥ 0.98 | T1 | 엔티티당 100 | 결정적 규칙이므로 높아야 정상 |
| **L0 체크섬 엔티티** FPR | ≤ 0.005 | T1 음성 | 1,375 | 부록 A.1 예측(주민번호 ~250배 감소)에서 도출 |
| **L1 전담**(PERSON/ADDRESS) char-recall | ≥ 0.85 | T1 + T3 | 엔티티당 100 | KDPII 참조 사례 F1 0.848 수준 |
| **L1 전담** FPR | ≤ 0.05 | T1 음성 | 1,375 | |
| **L1-ATK 주 헤드** 재현율 | **≥ 0.75** | T4 | 셀당 100 | **§7.1.2 참조 — 교사 R 0.748이 사실상 상한** |
| **L1-ATK** FPR | ≤ 0.02 | T4 benign | 700 | **로컬 도구는 과탐이 곧 우회다** |
| **code 타입 PII** FPR | ≤ 0.08 | T1 code 세그먼트 | 375 | prose 0.05보다 완화 — 근본적으로 어렵다 |
| **타입 감지 정확도** (§2.6.2) | ≥ 0.95 | T1 전체 | 2,500 | |
| 지연 p50 (`interactive`, P2, 단일 세그먼트) | < 300ms | 벤치 하네스 | 100회 | §1.2 |
| **지연 p95** (`interactive`, P2, **3세그먼트**) | **< 900ms** | 벤치 하네스 | 100회 | §7.1.3 |

**미달 시 행동**: 목표를 낮추지 않고 **미달 사실을 보고**한다. 평가 원칙 3(동어반복 금지)의 연장이다.

#### 7.1.2 ★ L1-ATK 재현율 목표를 0.75로 둔 이유 — 교사가 상한이다

앞선 초안은 0.80이었다. **틀렸다.**

교사 `kanana-safeguard-prompt-2.1b`의 **F1 0.844는 P 0.968 / R 0.748의 조합**이다. 목표 지표가 **재현율**이므로 비교 대상은 F1이 아니라 **R 0.748**이다. 0.80은 "허용 저하"가 아니라 교사 대비 **+0.052 초과 요구**다 — 증류 학생에게 교사보다 높은 재현율을 요구하는 셈이다.

우회 벡터 추가 학습(§6.2)으로 교사를 넘을 **가능성은 있으나 그것은 가설이지 목표가 아니다.**

→ **목표 0.75(교사 동급). 교사 초과 시 그 자체를 결과로 보고한다.**

**연쇄 모순도 함께 고친다** — L2-fast(kanana, R 0.748)는 L1이 애매하다고 넘긴 것을 받는데, 재현율이 원본보다 낮으면 에스컬레이션이 성능을 떨어뜨린다.
→ **L2-fast의 `SAFE` 판정은 확정 근거로 쓰지 않는다**(§6.4.3). P 0.968이므로 **`UNSAFE`만 신뢰**하고, `SAFE`면 L1의 원래 판정을 유지한다. 에스컬레이션은 **재현율을 올리는 경로가 아니라 정밀도를 올리는 경로**다.

#### 7.1.3 ★ 지연 예산 재계산 — 다중 세그먼트가 기본이다

단일 세그먼트 예산은 L0 20 + 타입 감지 5 + L1-PII 150 + L1-ATK 100 = **275ms**.

그런데 §5.3.3대로 **code 15% + structured 15% + mixed 5% = 35%가 다중 세그먼트 후보**다. 세그먼트 3개면 L1이 3회 돈다.

| 구성 | L0 | 타입감지 | L1-PII | L1-ATK | 분할·병합 | 합 |
|---|---|---|---|---|---|---|
| 단일 세그먼트 | 20 | 5 | 150 | 100 | 0 | **275ms** |
| **3 세그먼트** | 20 | 15 | 450 | 300 | **15** | **800ms** |

**p50은 275ms로 §1.2의 300ms를 지키지만, p95는 800ms대다.** 이것을 숨기지 않는다.

→ §7.1.1에 **p95 별도 목표(900ms)** 를 둔다. 그리고 완화 수단 셋을 W5에 측정한다: ① 세그먼트 배치 추론(가장 유력) ② 짧은 세그먼트 병합 후 1회 추론 ③ prose 세그먼트만 L1-ATK 실행.

⚠️ 이 수치는 **P2 기준 예산이지 실측이 아니다**(평가 원칙 5). W1 첫날 실측으로 갱신한다.

#### 7.2.1 ★ FPR 분모 — 하나로 못박는다

현재 문서가 세 단위로 혼용될 여지가 있다(문자열 건당 / 문서 건당 / 엔티티별). 다음으로 고정한다.

**전체 FPR 분모 = "음성 세그먼트 건당."** 세그먼트는 §5.3.4의 인스턴스 1건이다.

**엔티티별 FPR 분모 = "전체 음성 세그먼트"** — 형식 혼동 음성이 아니다.

이 선택이 수치를 수십 배 가른다. T1 2,500건 중 음성이 1,375건(무효 체크섬 500 + 형식 유사 625 + 완전 무해 250)인데,
- **전체 음성 분모(1,375)**: 목표 FPR 0.005 → 허용 오탐 6.9건 → **검증 가능**
- 형식 혼동 음성 분모(엔티티당 ~78건): 목표 0.005 → 허용 0.39건 → 관측 하한이 1/78 = **0.0128로 목표의 2.6배** → **구조적으로 검증 불가**

→ **전체 음성 세그먼트를 분모로 쓴다.** 형식 혼동 음성 기준 수치는 **보조로 병기**하되 목표 판정에는 쓰지 않는다.

부록 A.1의 "무작위 숫자열 통과율 ~10%"처럼 다른 단위를 쓰는 곳은 **그 자리에 단위를 명시**한다.

#### 7.2.2 타입별 분리 보고 (§2.6 검증)

**평균에 묻히면 "코드가 섞인 프롬프트에서 오탐 폭발"이 안 보인다.**

```
타입          char-recall   FPR      n(음성 세그먼트)
prose           0.xxx      0.xxx        825
code            0.xxx      0.xxx        206   ← 여기가 무너지기 쉽다
structured      0.xxx      0.xxx        206
log             0.xxx      0.xxx         69
mixed           0.xxx      0.xxx         69
[대조] 타입 조건화 OFF                          ← 기능의 실제 기여
```

**베이스라인에 "타입 조건화 OFF"를 추가한다**(§7.3). 기여가 측정되지 않으면 잘라낸다 — §8.4의 절삭 항목이다.

| **Gemini API 기반 판정** | 클라우드를 쓸 수 있다면 얼마나 잘하는가 = 온디바이스가 치르는 정확도 대가 (§7.4) |

### 7.4 테스트에 Gemini·OpenAI API를 어떻게 쓰는가

브리프가 *"test for prefer to use google model (ex gemini API)"* 를 요구한다. **프로그램의 탐지는 온디바이스이고, API는 세 자리에서 쓴다.**

| 자리 | 용도 | 모델 |
|---|---|---|
| **① 보호 대상 (검사 대상)** | 검사기가 통과시킨 프롬프트가 실제로 나가는 곳. 마스킹→응답→복원 왕복 검증 | **Gemini** (기본) / OpenAI (호환성 확인) |
| **② 정확도 상한 기준선** | 같은 코퍼스를 Gemini에 판정시켜 **온디바이스가 치르는 대가를 정량화** | Gemini |
| **③ 합성 코퍼스 생성 보조** | 템플릿 다양화·자연스러운 한국어 업무 문장 생성 | Gemini |

⚠️ **③에는 실제 개인정보를 절대 넣지 않는다.** 합성 값만 조립하고, 문장 골격 생성에만 쓴다.
⚠️ **Gemini free tier는 데이터가 학습에 쓰이므로** ①②③ 어디에도 실제 프롬프트를 쓰지 않는다. 평가는 합성 코퍼스로만 하고, 유료 tier를 쓴다.

②가 특히 중요하다. "온디바이스라서 정확도를 얼마나 포기했는가"는 이 제품의 핵심 트레이드오프인데 **아무도 수치로 답하지 않는다.** 우리가 답한다.

### 7.5 한국어 시크릿 벤치마크가 없다 — 기여 지점

조사 결과 시크릿 탐지 벤치마크는 CredData·SecretBench·FPSecretBench가 있으나 **전부 영어 코드 저장소 기준이고, 한국어 산문 대상 벤치마크는 공개된 것이 없다.**

→ **한국어 프롬프트 기준 시크릿·기밀표식 탐지 평가셋을 만드는 것 자체가 기여다.** 국내 서비스 키(토스·카카오·NCP·공공데이터포털)와 기밀 표식(대외비·영업비밀)을 포함하고, §6.3의 템플릿 분할과 누수 검사를 동일하게 적용한다.

### 7.6 평가 원칙 5조

1. **평가 설계 고정** — 지표·n·통계 방법을 데이터 생성 착수 전 **별도 커밋**으로 고정. git 이력으로 선후가 확인 가능해야 한다
2. **재현율 옆에 항상 FPR** — 예외 없다
3. **동어반복 금지** — 헤드라인은 "이 시스템이 질 수 있는가" 테스트를 통과해야 한다
4. **n은 군집 단위로** — 템플릿×변형의 곱을 행 수로 세지 않는다
5. **지연은 하드웨어·입력 길이 선언 후** — 사양 없는 지연 수치는 보고하지 않는다. **예산으로 잡을 때도 마찬가지다**

| # | 경로 | 판정 |

### 8.4 절삭 순서 — 미달 시

**잘라낸 것은 반드시 기록한다.** 조용히 사라지게 두지 않는다.

1. **L2 2-모델 하이브리드** (선택, 2.5일) — L1까지만으로 `interactive` 모드는 완결된다
2. 로컬 프록시 모드 (2.0일) — 라이브러리·CLI로 충분
3. **L1 백본 3종 비교 → A.X-Encoder 단독** (2.0일 + GPU 25.5h) — 기본값을 그대로 쓰고 "비교하지 않았다"를 한계에 명시
4. 베이스라인 7종 → 3종 (정규식 단독, vanilla Presidio, 타입 조건화 OFF)
5. **입력 타입 조건화** (4.0일) — §7.2.2의 ON/OFF 대조에서 기여가 측정되지 않으면 **먼저 자른다.** 측정 결과가 있으면 순위를 3번으로 올린다
6. T3 골드셋 n=200 → n=100 (Wilson 구간과 함께 보고)
7. **R2 공격 분류기** — 규칙 기반 우회 탐지(§2.3)만으로 축소. 이때 A-INJ·A-JB·A-KO-03·A-KO-06을 못 잡게 되고, 그 사실을 한계에 명시
8. R1은 마지막까지 지킨다 — H1을 지탱한다

**5번의 순위가 조건부인 이유**: 타입 조건화는 §9의 차별화 8번이지만 **기여가 측정되지 않으면 차별화가 아니라 미측정 주장**이다. 데이터가 판단한다.

## 9. 무엇이 의미 있는가

이 프로젝트가 기존에 없는 것을 만드는 지점은 **여덟**이다.

1. **한국 고유 식별자 + 체크섬 검증** — Presidio는 기본이 영어 전용이고, Google Cloud SDP에 한국 infoType 6종이 있지만 **클라우드로 데이터를 보내야 한다.** 갭은 "탐지기가 없다"가 아니라 **"데이터를 내보내지 않고 쓸 수 있는 탐지기가 없다"** 이다
2. **가역 정규화 후 재검사** — 우회 방어를 분류기가 아니라 결정적 규칙에 둔다. 설명 가능하고 우회가 어렵다
3. **고정밀 정규화 규칙의 발동을 회피 신호로** — 제로위드·태그문자·homoglyph·자모분해는 정상 한국어에서 발동률 0%다(실측). 반면 델타 총량은 신호가 아니라는 것도 실측으로 확인했다 — 들여쓰기 문서가 어떤 우회보다 델타가 높다
4. **★ token efficiency의 한국어 역전 발견** — 최신 시크릿 탐지 기법(Betterleaks)이 **한국어에서 신호가 뒤집힌다**는 것을 실측했다. 한국어 산문(eff 1.08)이 실제 시크릿(1.48)보다 낮아 임계 2.5 적용 시 **한국어 문장 100%가 오탐**된다. ASCII 게이트로 100%→0%로 해소되는 것까지 검증했다. **이건 이 프로젝트 밖에서도 유효한 발견**이고, 재현 스크립트를 함께 공개한다 ([probe](token_efficiency_probe.py) · [fix](token_efficiency_fix.py))
5. **한국어 우회 벡터 벤치마크 + 한국어 시크릿 평가셋** — 둘 다 공개 자산이 없다. 국내 서비스 키(토스·카카오·NCP·공공데이터포털)와 기밀 표식을 포함한다
6. **FPR 공개** — 국내 8개 제품 중 오탐률을 수치로 공개한 곳이 하나도 없다
7. **온디바이스가 치르는 정확도 대가의 정량화** — 같은 코퍼스를 Gemini API에 판정시켜 상한을 재고, 온디바이스와의 격차를 공개한다(§7.4). 이 트레이드오프를 수치로 답한 사례를 찾지 못했다
8. **★ 입력 타입 조건화 PII 판정** — 코드·JSON·로그가 섞인 프롬프트에서 정책을 **세그먼트 단위로 자동 전환**한다(§2.6). 조사 범위에서 이를 제품 기능으로 문서화한 사례도, 정면으로 다룬 논문도 확인하지 못했다. Presidio가 주는 것은 정적 allow list·임계값뿐이다. **타입 조건화 ON/OFF 대조로 기여를 정량화**하고(§7.2.2), **기여가 측정되지 않으면 차별화 주장을 철회하고 기능을 잘라낸다**(§8.4)

⚠️ 4·8번의 "없다"는 **검색 실패일 수 있다.** 문서에는 "확인하지 못했다"로 쓰고 단정하지 않는다.

### A.1 체크섬 오탐 감소

1차로 무작위 숫자열 10만 건씩 시험했다 — 주민번호 9.89% · 사업자 9.97% · 법인 10.03% · Luhn 9.99% 통과, 즉 **약 10배 감소**.

2차로 **현실적 오탐원**(주문번호 `YYMMDD-일련`, 입사일 기반 사번, 송장번호) 각 2만 건으로 재측정했더니 주민번호가 훨씬 크게 줄었다.

| 오탐원 | 정규식 단독 | +체크섬 | +생년월일·성별코드 | 감소 |
|---|---|---|---|---|
| 주문번호 | 88.9% | 8.8% | **0.34%** | **265배** |
| 사번 | 100% | 10.2% | **0.43%** | **235배** |
| 송장번호 | 100% | 9.7% | **0.36%** | **282배** |
| 제품 시리얼(사업자 형식) | 100% | 10.1% | — | 10배 |

**3중 검증이 체크섬 단독보다 25배 더 걸러낸다.** 그래서 예측값을 엔티티별로 나눴다.
### A.2 정규화 체인 — 델타 총량은 신호가 아니다

체인을 프로토타입으로 만들어 시험했다([normalize_probe.py](normalize_probe.py)). 우회 벡터는 전부 복원됐다 — `ㅁㅜㅅㅣㅎㅐ`→`무시해`, `無視`→`무시`, 제로위드 제거, 키릴 homoglyph→라틴, 전각→반각.

처음엔 **델타 비율만으로 정상/우회가 분리됐다**(정상 0.000 vs 우회 0.053~0.214). 그런데 **정당하게 정규화되는 한국어**를 넣자 무너졌다.

| 정상인데 정규화가 일어나는 경우 | 델타 비율 |
|---|---|
| 들여쓰기 있는 문서 (`1. 개요\n   2. 범위`) | **0.346** ← 어떤 우회 시도보다 높다 |
| 한자 병기 (`본 계약의 秘密유지 조항`) | 0.087 |
| 전각 혼입 (`제품코드 ＡＢＣ－１２３`) | 0.040 |

**규칙별 정밀도가 완전히 갈린다** (정상 10건 · 우회 6건 기준):

| 규칙 | 정상 발동 | 판정 |
|---|---|---|
| **zero-width 제거** | **0/10** | ★ 고정밀 — 발동 자체가 신호 |
| **태그 문자 제거** | **0/10** | ★ 고정밀 |
| **homoglyph 치환** | **0/10** | ★ 고정밀 |
| **자모 조합 복원** | **0/10** | ★ 고정밀 |
| NFKC (전각) | 3/10 | 저정밀 — 정규화는 필요하나 신호 아님 |
| 한자→한글 | 2/10 | 저정밀 |
| 공백 정규화 | 2/10 | 저정밀 |

→ **교정: 델타 총량이 아니라 고정밀 규칙의 발동만 신호로 쓴다.** 고정밀 4종만 쓰면 정상 오탐 0%이지만 재현율은 33%에 그친다. **나머지 우회(한자·전각·공백)의 가치는 델타가 아니라 재검사에 있다** — `無視`를 `무시`로 바꾼 뒤 다시 검사해서 공격이 잡히는 것이 목적이지, "한자가 있었다"는 사실 자체는 신호가 아니다.

⚠️ 구현 주의: 프로토타입의 자모 조합 카운트가 길이 기반이라 부정확했다. 실제 구현은 **조합된 음절 수를 직접 세야** 한다.

이 접근의 장점은 세 가지다. **설명 가능하다**(어느 규칙이 무엇을 바꿨는지 로그에 남는다), **우회가 어렵다**(정규화를 피하려면 정규화되지 않는 형태여야 하는데 그러면 모델도 못 읽는다), **학습이 필요 없다**(A-ENC·A-KO의 절반이 규칙만으로 잡힌다).

### A.3 token efficiency의 한국어 역전

Betterleaks/Aikido가 제안한 **token efficiency**(`eff = 문자수 / BPE 토큰수`, 임계 2.5 미만이면 시크릿 의심)는 엔트로피보다 훨씬 낫다고 보고됐다(F1 0.725 vs 0.325). **한국어에서 어떻게 되는지 직접 측정했다**([token_efficiency_probe.py](token_efficiency_probe.py), cl100k_base).

| 집단 | n | 평균 eff | 임계 2.5 적용 |
|---|---|---|---|
| **한국어 산문** | 10 | **1.08** | **오탐 10/10 = 100%** |
| 영어 산문 | 10 | 5.61 | 오탐 0/10 = 0% |
| 실제 시크릿 (8종) | 80 | **1.48** | 탐지 80/80 = 100% |

**한국어 산문(1.08)이 실제 시크릿(1.48)보다 낮다.** 10개 문장 전부가 시크릿 평균 아래다. 즉 이 방법은 한국어에서 **저하되는 게 아니라 역전된다** — 영어에서는 "eff 낮음 = 시크릿"이지만 한국어 문서에서는 "eff 낮음 = 그냥 한국어"다. 원인은 cl100k/o200k가 영어 중심으로 학습돼 한글이 음절당 1~2 토큰으로 잘게 쪼개지기 때문이다.

**수정과 검증** ([token_efficiency_fix.py](token_efficiency_fix.py)) — 시크릿은 정의상 ASCII이므로, **ASCII 게이트를 먼저 통과한 12자 이상 덩어리에만** token efficiency를 적용한다.

| | 한국어 문장 오탐 | 한국어 문장 속 시크릿 탐지 |
|---|---|---|
| 수정 전 (문장 전체에 적용) | **100%** | — |
| **수정 후 (ASCII 게이트)** | **0%** | **100%** |

같은 함정이 **문자 단위 엔트로피**에도 있다. 한글 완성형은 11,172자 조합이라 문자당 unigram 엔트로피가 영문(≈4)보다 훨씬 높다. **charset 게이트 없이 "엔트로피 > 4.5" 룰을 자체 구현하면 평범한 한국어 단어가 전부 걸린다.** (detect-secrets는 base64/hex charset으로 후보를 제한해서 우연히 이 문제를 피한다.)

→ **L-SEC-05의 순서를 못박는다**: ① ASCII charset 게이트 → ② 길이 ≥12 → ③ 플레이스홀더·사전단어 필터(`YOUR_API_KEY`, `xxxxxxxx` 등) → ④ 근접 키워드 확인 → ⑤ 그 다음에 token efficiency/엔트로피.

### A.4 조사 교정의 적용 범위

프로토타입으로 왕복을 시험하다가 **과교정 버그**를 찾았다([vault_probe.py](vault_probe.py)).

교정 규칙을 텍스트 전체에 정규식으로 걸면 **조사처럼 보이지만 단어의 일부인 음절**을 훼손한다. 호격 조사 `아/야`가 특히 위험하다.

| 원문 | 전체 적용 시 | |
|---|---|---|
| 이케아 매장에 | **이케야** 매장에 | ★ 훼손 |
| 노키아 단말을 | **노키야** 단말을 | ★ 훼손 |
| 볼리비아 커피 | **볼리비야** 커피 | ★ 훼손 |

위험 케이스 10건 중 3건이 훼손됐다.

**수정 두 가지.** ① 교정을 **복원된 토큰 바로 뒤 조사에만** 적용한다 — 토큰이 없는 텍스트는 아예 건드리지 않는다. ② **호격 `아/야`를 교정 대상에서 제외**한다. 이/가, 을/를, 은/는, 과/와, 으로/로 다섯 쌍만 다룬다.

수정 후 재시험: **복원 7/7 통과, 원문 훼손 0/6.** 토큰 변형 내성(`<person_1>` 소문자, `< PERSON_1 >` 공백)과 `ㄹ` 받침 예외(`서울로` vs `부산으로`)도 함께 통과한다.

실제로 확인했다([josa_probe.py](josa_probe.py)) — 이/가, 을/를, 은/는, 과/와, 아/야, 이라/라 6쌍과 `ㄹ` 받침 예외(`서울로` vs `부산으로`)까지 9개 케이스가 종성 계산만으로 전부 통과한다. **LGPL 의존을 피할 수 있다.**
