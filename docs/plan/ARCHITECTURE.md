## 1. 전체 구조

```
사내 클라이언트 (OpenAI 호환 SDK / curl)
      │
      ▼
┌──────────────────────────────────────────────────────────────┐
│  LiteLLM Proxy  +  GarimGuardrail (CustomGuardrail 서브클래스) │
│                                                              │
│  pre_call    ── L0 볼트 redact (정규식 + 체크섬)               │
│                 L1 PII NER (privacy-filter-korean, CPU)      │
│                 L1 인젝션 레일 (kanana-prompt-2.1b)           │
│                 tool 롤 메시지 검사 + taint 태깅               │
│                 정책 판정 → allow / mask / warn / block       │
│                                                              │
│  ────────────  업스트림 호출 (Gemini API 또는 로컬 Gemma 4)     │
│                                                              │
│  post_call   ── assistant tool_calls 인자 검사 (§5)           │
│                 응답 PII 스캔                                 │
│                 볼트 rehydrate (조사 처리, §3)                 │
│                                                              │
│  logging_only ─ 비동기 감사 라벨링 (kanana 8b / siren-8b)      │
│                                                              │
│  정책 엔진: YAML 정책 테이블 (§6)                              │
│  감사: JSONL 이벤트 스트림 (§7)                                │
└──────────────────────────────────────────────────────────────┘
      │                                    │
      ▼                                    ▼
  업스트림 LLM                    관리·감사 API (FastAPI 사이드카)
  Gemini / Gemma 4 로컬           정책 조회 · 감사 조회 · warn 승인 큐
```

동기 경로에 있는 모든 모델은 로컬에서 돈다(§8). 외부로 나가는 것은 마스킹된 프롬프트뿐이다.

## 2. 인터셉션 지점 결정

### 결정: API 레이어 — OpenAI 호환 리버스 프록시

[MARKET_RESEARCH §3.3](MARKET_RESEARCH.md#33-인터셉션-3방식-비교)의 세 방식 중 API 레이어를 택한다.

| 대안 | 기각 사유 |
|---|---|
| **브라우저 확장** | 기술 스택이 다르고(JS/MV3), 앱별 DOM 후킹은 시그니처 유지보수가 지속 비용이다. 무엇보다 tool-call 층(축 C)이 보이지 않는다 |
| **인라인 네트워크 프록시** | 대규모 SSL 인터셉션은 인증서 배포·피닝 회피·TLS 1.3/QUIC 대응이 필요한 조직 규모의 문제다. 솔로 범위 밖 |

**API 레이어를 택함으로써 못 보는 것을 명시한다**: 직원이 브라우저로 chatgpt.com에 직접 붙어 쓰는 사용은 이 게이트웨이를 통과하지 않는다. 즉 이 설계는 *사내 애플리케이션과 에이전트의 LLM 사용*을 통제하며, *개인 브라우저 사용 통제*는 다른 계층의 문제다. SecureBridge를 비롯한 상용 제품이 이 두 가지를 모두 다루는 것과의 차이다.

### 본체: LiteLLM (자체 프록시를 만들지 않는다)

구 프로젝트는 자체 FastAPI 서비스에 ReAct 루프까지 직접 구현했다. 그 경험이 있으므로 다시 만들 수 있지만, **만들지 않는다.**

프록시가 실제로 해야 하는 일 — SSE 스트리밍 패스스루, 프로바이더별 인증·재시도·타임아웃, 모델 라우팅과 폴백, 토큰 카운팅, 100+ 프로바이더의 요청/응답 스키마 변환 — 은 전부 커머디티이고 LiteLLM(MIT)이 이미 한다. 5주 예산을 여기 쓰면 차별화 축 A·C에 쓸 시간이 없다.

**대신 기존 FastAPI 경험은 관리·감사 API 사이드카로 재사용한다**: 정책 조회, 감사 로그 조회, warn 모드의 승인 큐. `src/agent/server.py`의 principal 기반 authz와 idempotency 패턴, `src/agent/hitl.py`의 승인 큐가 그대로 옮겨간다([ASSET_REUSE.md](ASSET_REUSE.md)).

**리스크**: LiteLLM 훅 API의 버전 변동. 버전을 lock으로 고정하고 훅 어댑터를 얇게 유지해 교체 비용을 낮춘다([기획서 R5](기획서.md#6-예상-문제점-및-대처-방안)).

## 3. 심(seam) 매핑 — 구 4-seam에서 LiteLLM 훅으로

구 프로젝트의 `before_model / after_model / before_tool / after_tool` 4-seam은 자체 ReAct 루프 안에 있었다. LiteLLM 위에서는 훅 4종으로 수렴한다.

| LiteLLM 훅 | 하는 일 | 구 seam 대응 |
|---|---|---|
| **`pre_call`** | 볼트 redact → PII NER → 인젝션 레일 → tool 롤 메시지 검사 → 정책 판정 | `before_model` + `after_tool` (도구 결과가 다음 요청의 메시지로 재주입되므로 같은 지점에서 만난다) |
| **`post_call`** | assistant `tool_calls` 인자 검사 + taint 전파 → 응답 PII 스캔 → 볼트 rehydrate | `after_model` + `before_tool` |
| **`during_call`** (스트레치) | Qwen3Guard-Stream 토큰 단위 판정 | 구 프로젝트에 대응 없음 |
| **`logging_only`** | kanana 8b / siren-8b 비동기 라벨링 | 구 프로젝트의 log-only rail |

> **구조적 차이 하나를 정직하게 기록한다.** 구 프로젝트는 자체 루프를 소유했기 때문에 도구를 *실행하기 직전*에 개입할 수 있었다(`before_tool`). LiteLLM 위에서는 도구 실행이 클라이언트 쪽에서 일어나므로, 게이트웨이는 모델이 tool call을 *제안한 시점*(`post_call`)에만 개입한다. 즉 **차단이 아니라 거부 신호**다. 클라이언트가 게이트웨이의 판정을 무시하고 도구를 실행하는 것을 물리적으로 막을 수는 없다. 이 한계는 §5에서 다시 다룬다.

## 4. 가드 캐스케이드와 레이턴시 예산

원칙: **저비용 결정적 검사를 앞에, 모델 추론은 예산 안에서만 동기로, 큰 모델은 전부 비동기로.**

| 계층 | 컴포넌트 | 동기성 | 예산 | 판정 |
|---|---|---|---|---|
| **L0** | 한국어 정규식 8종 + 체크섬 검증 + 볼트 마스킹 | sync | < 10ms | 결정적. 여기서 걸리면 아래를 볼 필요 없는 경우가 대부분 |
| **L1-PII** | `privacy-filter-korean` (active 50M, CPU) — 정규식이 못 잡는 문맥 의존 엔티티(성명, 주소) | sync | 입력 합계 **p50 < 100ms** | 정규식 스위트와 **보완 관계**. 어느 쪽이 어떤 엔티티에서 이기는지는 [기획서 §5.2](기획서.md#52-베이스라인)에서 측정 |
| **L1-INJ** | `kanana-safeguard-prompt-2.1b` — 단일 토큰 출력이라 1토큰 생성으로 판정 | sync | 상동 | GPU 부재 시 휴리스틱 폴백. **폴백 사실을 감사 로그에 기록**한다 (구 프로젝트에서 조용한 폴백이 문제였다) |
| **L2** | 응답 PII 스캔 + 볼트 rehydrate | sync | **p50 < 150ms** | |
| **L3** | `kanana-safeguard-8b` (유해성), `kanana-safeguard-siren-8b` (법적·개인정보 리스크) | **async** | 무제한 | 감사 라벨링 전용. 동기 경로 성능에 영향 없음. GPU 없으면 생략 가능하도록 설계 |

**예산 근거**: 업계 관측치는 소형 BERT 분류기 ~50ms, 목적 특화 guard 모델 ~29ms, LLM-as-judge 5~8.6초다. 입력 레일 p50 200ms를 넘으면 가드레일이 제품 병목이 된다([MARKET_RESEARCH §3.4](MARKET_RESEARCH.md#34-참고-수치)).

**초과 시 대응 순서** (무엇을 뺐는지 반드시 기록): ① L1-PII와 L1-INJ의 병렬 fan-out → ② 캐스케이드 조기 종료(L0에서 block 판정이면 L1 생략) → ③ 해당 검사를 비동기로 이동.

**8B 모델을 동기 경로에서 뺀 이유**: F1이 높다는 이유로(kanana-8b 0.946) 동기 경로에 넣으면 예산이 무너진다. 성능이 좋은 모델을 성능이 필요 없는 자리에 배치하는 것이 옳다.

## 5. 한국형 PII 스위트와 가역 마스킹 볼트 — 축 A

### 5.1 엔티티 8종과 체크섬

| 엔티티 | 형식 | 검증 |
|---|---|---|
| 주민등록번호 | 13자리 | 가중치 체크섬 + 생년월일 유효성 + 성별코드 정합 |
| 외국인등록번호 | 13자리 | 체크섬 (성별코드 범위가 내국인과 다름) |
| 여권번호 | M/S 접두 + 8자리 | 형식 |
| 운전면허번호 | 지역코드 + 12자리 | 지역코드 사전 |
| 사업자등록번호 | 10자리 | 가중치 체크섬 |
| 법인등록번호 | 13자리 | 체크섬 |
| 계좌번호 | 은행별 자릿수 패턴 | 패턴 사전 |
| 카드번호 | 16자리 | **Luhn** |

**체크섬이 핵심이다.** 정규식만 쓰면 주문번호·사번·제품 시리얼처럼 형식이 유사한 문자열을 전부 PII로 오탐한다. 이것이 [기획서 S1](기획서.md#22-정량-지표)에서 정규식 단독을 베이스라인으로 두고 FPR 감소를 측정하는 이유다.

추가로 **한국어 문맥 단어 사전**을 붙인다 — "주민번호", "계좌", "연락처", "성함", "사업자" 등. Presidio는 문맥 단어로 confidence를 보정하는데, 기본 사전이 영어뿐이라 한국어에서는 이 메커니즘이 작동하지 않는다. 구 프로젝트가 확인한 **Presidio 한국어 결함 2건**(`KrPassportRecognizer.supported_language`가 ISO-3166 국가코드 `"kr"`로 잘못 설정돼 `language="ko"` 파이프라인에서 로드되지 않음 / `KrRrnRecognizer.context`가 영어 문자열 6개뿐이라 한글 문맥 부스트가 없음)이 정확히 이 지점이며, 업스트림 PR 후보다.

### 5.2 가역 마스킹 볼트

기존 `src/dlp/vault.py`의 `RegexVault`가 이미 요청 스코프 `redact` / `rehydrate` / `restore`와 값 단위 coreference(같은 원본값 → 같은 토큰)를 구현했다. 이것을 코어로 쓰고 두 가지를 더한다.

**(a) 조사 결합 처리.** 이 문제는 두 곳에서 나온다.

| 상황 | 문제 | 대응 |
|---|---|---|
| 순수 토큰화 (`홍길동` → `<PERSON_1>`) | 원문 `홍길동이`는 `<PERSON_1>이`가 되고 복원하면 `홍길동이`로 정확히 돌아온다. **여기는 문제없다** | — |
| **LLM이 조사를 새로 생성** | 모델이 `<PERSON_1>` 뒤에 조사를 붙일 때 토큰의 종성을 알 수 없어 `<PERSON_1>가`를 쓸 수 있다. 복원하면 `홍길동가` — 비문 | 복원 시 앞 음절의 종성을 보고 이형태 조사(이/가, 을/를, 은/는, 과/와, 으로/로)를 교정 |
| **가명 치환** (`홍길동` → `김민준`) | 종성 유무가 바뀌면 조사도 바뀌어야 한다 | 위와 같은 교정 로직. 가명 치환은 스트레치 |

**(b) 토큰 변형 내성.** 기존 `restore`는 정확 매칭만 복원하므로 모델이 `<email_1>`이나 `< EMAIL_1 >`로 변형하면 복원되지 않는다(기존 코드가 이미 알려진 한계로 기록해 둔 사항이다). 대소문자·공백에 관용적인 매칭을 추가하되, **관용 매칭이 과하면 오복원 위험**이 있으므로 허용 범위를 명시하고 테스트로 고정한다.

**(c) 유출 검사의 범위 한계를 유지.** 기존 `contains_raw`는 볼트가 *이미 매핑한* 값만 검사한다. 모델이 새로 생성했거나 탐지기가 놓친 PII는 여기서 잡히지 않는다. 이 한계는 기존 코드에 정직하게 기록돼 있고, 새 문서에서도 유지한다 — "PII 유출 0%"는 *탐지·토큰화된 PII에 한정*한 주장이다.

## 6. tool-call DLP — 축 C

### 6.1 무엇을 하는가

두 방향을 본다.

| 방향 | 검사 | 훅 |
|---|---|---|
| **나가는 쪽** — assistant가 제안한 tool call의 인자 | 인자 문자열에 PII가 있는가. 있으면 마스킹 또는 거부. egress 성격의 인자(수신자 주소, 계좌)는 allowlist 검사 | `post_call` |
| **들어오는 쪽** — tool 롤 메시지(도구 반환값) | 비신뢰 출처로 태깅하고, 인젝션 레일로 스캔하며, 다음 요청에서 이 내용이 tool 인자로 흘러갔는지 추적 | `pre_call` |

### 6.2 provenance 추적

구 프로젝트의 `src/agent/taint.py`가 이미 `Tainted(value, sources)` 래퍼와 재귀적 `sources_of()` 전파를 구현했다. 더 중요한 것은 거기서 발견한 **value-provenance** 접근이다: 모델이 라운드트립하면서 래퍼가 세탁되므로(모델이 낸 args는 순수 문자열이라 `sources_of() == frozenset()`), **인자 값이 비신뢰 도구 출력의 부분문자열인지**를 별도로 검사해야 실제로 작동한다. 이 통찰을 그대로 가져온다.

이론적 배경은 CaMeL(arXiv:2503.18813)의 provenance/capability 모델이다. 다만 CaMeL은 전용 인터프리터를 요구하고, 본 프로젝트는 게이트웨이 레벨의 경량 근사다 — **증명 가능한 보안이 아니라 실용적 차단**이며 그 차이를 문서에 명시한다. 기존 `taint.py`가 ARGUS(arXiv:2605.03378)를 선행연구로 명시하고 신규성을 주장하지 않은 태도도 유지한다.

### 6.3 구조적 한계

§3에서 언급한 것을 다시 적는다. **게이트웨이는 도구를 실행하지 않으므로 실행을 물리적으로 막을 수 없다.** 할 수 있는 것은:

1. tool call 인자를 마스킹해서 응답한다 — 클라이언트가 그대로 실행하면 마스킹된 값이 도구로 간다
2. 정책 위반을 응답에 명시하고 감사 로그에 남긴다
3. warn 모드에서 승인 큐로 보낸다

**"차단했다"고 주장하려면 클라이언트가 게이트웨이의 판정을 따른다는 전제가 필요하고, 그 전제를 문서와 평가 보고 양쪽에 명시한다.** 이 전제 없이 차단율을 보고하면 구 프로젝트의 동어반복 지표와 같은 실수가 된다.

v1은 LiteLLM 메시지 레벨(assistant `tool_calls` + tool 롤 메시지)로 한정한다. 도구 실행 지점까지 소유하는 독립 MCP 프록시는 [6주차 스트레치](ROADMAP.md#w6--버퍼--스트레치)다.

## 7. 정책 엔진

### 결정: in-process YAML 정책 테이블 (OPA/Rego 아님)

```yaml
# 개념 스케치 — 실제 스키마는 W2에서 확정
policies:
  - id: pii-default
    match: { route: "*", principal_group: "*" }
    entities:
      KR_RRN:        block      # 주민번호는 마스킹으로도 내보내지 않음
      KR_ACCOUNT:    mask
      KR_CARD:       mask
      KR_BIZNO:      allow      # 사업자번호는 공개정보인 경우가 많음
      PERSON:        mask
    tool_args:
      "*.recipient": { egress_allowlist: corp_domains }
    regulatory_tags: [pipc-guide-4, fsc-ai-2026]
```

**판정 4모드**:

| 모드 | 동작 |
|---|---|
| `allow` | 통과. 감사에는 탐지 사실만 기록 |
| `mask` | 볼트 토큰으로 치환 후 통과. 응답에서 복원 |
| `warn` | 승인 큐로 보내고 대기. 승인 시 통과, 미승인 시 타임아웃 거부 |
| `block` | 거부. 사유와 정책 ID를 응답에 포함 |

**기본값을 `block`이 아니라 `mask`로 둔다.** InjecGuard(arXiv:2410.22770)가 지적하듯 사내 게이트웨이에서 과탐은 즉시 우회(섀도우 AI)를 부른다. 지란지교 OfficeKeeper가 허용/차단/비식별화 3모드를 갖춘 것도 같은 이유로 보인다([MARKET_RESEARCH §2.1](MARKET_RESEARCH.md#21-제품별-요약)).

**OPA/Rego를 기각한 이유**: 솔로 5주 범위에 정책 엔진 운영(번들 배포, 데이터 문서, 정책 테스트 하네스)까지 얹는 것은 과잉이다. 다만 **스키마를 Rego로 컴파일 가능한 형태**(매칭 조건과 결정이 분리된 선언적 구조)로 설계해 전환 경로를 열어 둔다.

구 프로젝트의 `TierAGate`가 도구 스펙 → 인자 스키마 검증 → egress allowlist → taint → HITL 순으로 결정하는 구조는 그대로 이식한다. 다만 판정이 `Block` / `None` 이진이었던 것을 4모드로 확장한다.

**`warn` 모드의 승인 큐**는 `src/agent/hitl.py`(승인 큐)와 `src/agent/server.py`의 요청자≠승인자 분리, 승인 TTL, 금액 재검증 패턴을 재사용한다.

## 8. 감사 로그 스키마

JSONL 이벤트 스트림. JSON Schema 파일로 고정하고 테스트로 검증한다.

```jsonc
{
  "schema_version": "1.0",
  "request_id": "req_...",
  "ts": "2026-08-15T10:23:11.482Z",
  "principal": { "id": "svc-crm", "group": "cs-team", "tenant": "acme" },
  "upstream_model": "gemini-3.6-flash",
  "direction": "request",              // request | response | tool_call
  "detections": [
    {
      "entity_type": "KR_RRN",
      "span_hash": "sha256:...",       // ★ 원문은 저장하지 않는다
      "recognizer": "regex+checksum",
      "confidence": 0.99,
      "layer": "L0"
    }
  ],
  "action": "mask",                     // allow | mask | warn | block
  "policy_id": "pii-default",
  "rail": { "injection": 0.12, "fallback_used": false },
  "latency_ms": { "l0": 3, "l1_pii": 41, "l1_inj": 28, "total_sync": 74 },
  "vault_ref": "vault_...",             // 매핑 자체는 요청 스코프, 로그에는 참조만
  "regulatory_tags": ["pipc-guide-4", "ai-basic-act-record"],
  "retention_class": "audit-3y"
}
```

**설계 원칙**:

- **원문 미저장** — 탐지된 PII의 원문은 로그에 남기지 않고 해시만 남긴다. SecureBridge의 어드민 콘솔이 "원본 프롬프트"를 보여준다고 명시한 것과 다른 선택이며, 감사 가능성과 최소수집 원칙 사이의 트레이드오프를 문서에 기록한다.
- **`fallback_used` 명시** — GPU 부재로 휴리스틱 폴백이 쓰였으면 로그에 남긴다. 조용한 폴백은 성능 수치를 오염시킨다.
- **`latency_ms` 분해** — 계층별로 나눠 기록해야 예산 초과 시 어디가 문제인지 알 수 있다.
- **`regulatory_tags[]`** — [MARKET_RESEARCH §5](MARKET_RESEARCH.md#5-규제-앵커--기능-번역)의 규제별 요구를 태그로 매핑한다. 인공지능 기본법의 기록보관 의무, 개인정보위 안내서의 4단계 중 어느 단계에 해당하는지, 금융분야 AI 가이드라인의 어느 원칙인지. **이것이 글로벌 OSS가 만들어주지 않는 국내 특화 자산이다.**
- 메트릭은 구 프로젝트의 `src/agent/metrics.py`(카디널리티 가드, PII-free 스냅샷)를 재사용한다. 볼트가 이미 엔티티 타입만 카운트하고 원본 값은 절대 기록하지 않는 패턴을 지킨다.

## 9. 온디바이스 / API 분리 원칙

> **탐지는 전부 로컬, 생성만 외부.**

PII를 탐지하기 위해 PII를 외부 API로 보내는 것은 자기모순이다. Cloudflare AI Gateway를 기각한 이유이기도 하다([MARKET_RESEARCH §6.2](MARKET_RESEARCH.md#62-검토-후-기각)).

| 구분 | 위치 | 모델 | 라이선스 |
|---|---|---|---|
| **탐지 (가드)** | **전부 로컬** | privacy-filter-korean (50M active, CPU) · kanana-prompt-2.1b · kanana-8b/siren-8b (비동기, 선택적 GPU) · Qwen3Guard-Stream 0.6B (스트레치) | 전부 **Apache 2.0** |
| **생성 (업스트림)** | 외부 API 또는 로컬 | **Gemini API** (`gemini-3.6-flash`, 1순위) · **Gemma 4 E4B 로컬** (오프라인 데모, Apache 2.0) | — |

이 분리가 브리프의 두 요건을 동시에 충족한다:
- **"prefer to use google model"** → 업스트림 생성 LLM이 Gemini, 로컬 옵션이 Gemma 4 (브리프가 지목한 "gemma4"가 실재하며 **Apache 2.0**이다)
- **"prefer to use on-device model + 라이선스 확인"** → 가드 모델 전원 로컬 + 전수 Apache 2.0

그리고 N2SF·금융권의 폐쇄망 요건과도 맞는다. 완전 오프라인 구성(Gemma 4 로컬 + 로컬 가드)에서 게이트웨이 전체가 외부 통신 없이 동작하는 것을 데모로 보인다.

구 프로젝트는 같은 요건에 대해 "온디바이스 분류기를 강제 경계로 쓰면 안 된다"는 논지로 사실상 반박했고 헤드라인 실측은 전부 gpt-4o-mini로 냈다. 그 불일치가 재기획의 이유 중 하나다([기획서 §1.5](기획서.md#15-구-프로젝트safeagent-kr-대비-변경점)).
